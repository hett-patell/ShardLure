# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ShardLure derives **attacker identity** from SSH honeypot telemetry. It wraps the [Cowrie](https://github.com/cowrie/cowrie) SSH honeypot (a separate Python process), ingests Cowrie's JSON log + journald sshd lines, clusters attackers into **actors**, enriches their IPs against threat-intel feeds, and serves a live dashboard + forensic TUI. It also shares findings back out (MalwareBazaar payloads, AbuseIPDB reports, STIX IOCs).

Single Go module: `github.com/networkshard/shardlure` (Go 1.27). One binary, subcommand-dispatched from `cmd/shardlure/main.go`.

## Commands

```bash
make build          # go mod tidy && go build -o shardlure ./cmd/shardlure
make test           # go test ./...
make fuzz           # opt-in fuzzing of the 3 attacker-input parsers (FUZZTIME=5m to extend)
go test ./internal/store/ -run TestName   # single package / single test
go vet ./...        # CI runs this; keep it clean
```

**Fuzz targets** cover the three parsers that eat attacker-controlled bytes: `journal.FuzzParseLine`, `cowrie.FuzzParseReader`, `capture.FuzzDecodeTTYReader` (the packed `<iLiiLL` TTY struct — sharpest edge, since its own length arithmetic could over-read). CI does **not** fuzz, but `go test ./...` runs each target's seed corpus, so known-bad inputs stay covered. Only *failing* inputs get written to `testdata/fuzz/`, and those files are binary — don't commit them (`check-utf8.sh` would reject them); pin the finding as a readable unit test instead, as `TestParseLineSanitisesInvalidUTF8AndNUL` does.

CI (`.github/workflows/ci.yml`) runs on push to `main`, tags `v*`, and all PRs: `check-utf8.sh` → `go mod verify` → `go vet` → `go test -coverprofile` → build → `version` smoke → `ci-web-smoke.sh` (boots the web server and checks it serves). Then a cross-build job. There is **no separate lint step** beyond `go vet`; do not add one without asking.

Run locally after building:
```bash
./shardlure ingest journal testdata/sample.journal --replace   # see make run-sample
./shardlure ingest cowrie <cowrie.json> --replace
./shardlure actors [--limit=N]              # 1..1000, 0 = all (campaigns/scripts: 1..1000)
./shardlure reclassify cowrie [--dry-run]   # re-derive playbooks from persisted aggregates
./shardlure actor show <ip|actor-id>
./shardlure web :8080 [--tailscale]        # dashboard without ingest; runs the campaigns worker too, unless another process on the same DB holds its lease
./shardlure live :8080 --cowrie=<path>     # live ingest loop + dashboard (the real daemon)
./shardlure dashboard                       # forensic TUI (tui/app.go, bubbletea)
```

## Deploy workflow — the two non-obvious gotchas

1. **Never `scp` Go/Python sources to the VPS — it silently corrupts them to UTF-16.** Use `make deploy` (`scripts/push-sources.sh`, tar-over-SSH). CI enforces this with `scripts/check-utf8.sh`, which fails the build on any tracked file with a UTF-16 BOM or NUL bytes. If sources arrive mangled, `scripts/fix-go-sources.sh` / `scripts/repair-text.sh` repair them. This is why the check exists — respect it.

2. **Two independent installers, with inverted port defaults.** `scripts/install.sh` downloads a prebuilt release binary (no Go toolchain). `scripts/shardlure.py run` is the richer VPS wrapper: installs Go, *builds* from source, and does the interactive real-SSH-port migration. Their honeypot/admin port defaults are swapped — `shardlure.py` puts the honeypot on **22** and moves real sshd to **2222** (key-only); `install.sh` keeps admin on 22 and the honeypot on 2222. `sudo ./shardlure run` execs into `scripts/shardlure.py run`.

## Architecture

Data flows in one direction, and `pkg/models` (`Event`, `Actor`, `AggregatedActor`, `IPStat`, the `Kind*`/`Source*` consts) is the shared vocabulary that lets `store` and `actor` avoid an import cycle:

```
Cowrie :22 → cowrie.json ─┐
                          ├→ ingest → []Event → cluster → Actor → SQLite → web :8080 / TUI
journald sshd  ───────────┘                                          ├→ enrich (inbound IP rep)
                                                                      └→ share/report (outbound intel)
```

The Go binary and the Cowrie process are **separate systemd units with no IPC** — the only contract between them is the JSON log file on disk (`$DATA_DIR/cowrie/var/log/cowrie/cowrie.json`). `shardlure-live.service` `Wants=cowrie.service`.

### The live daemon is the conductor (`cmd/shardlure/runtime.go` `runRuntime`)
`cmdLive` (`main.go`) only parses flags; `shardlure live` and `shardlure web` both call `runRuntime`, which differs by `opts.Live`. It serves the web server (joined with two monitor samplers, `RunSampler` and `RunAggregateSampler`) and runs **up to eight background workers**, all sharing one `*store.Store` and one `*settings.Keystore`, under the lifecycle in `live_lifecycle.go` (root signal context, cancellable seed, every worker joined before the store closes). In `live` the seed step replays 30 days of journal (unless `--no-journal`), the rotated Cowrie logs and one capture run once the listener is bound; both modes then run `WarmCaches` before reporting ready.

**Under both `live` and `web`** (three workers):
1. **store timestamp backfill** (`runRuntimeBackfills`) — repairs pre-v19 artifact provenance/schedules, migrates legacy event times into the v20 exact nanosecond column, then canonicalises the v22 ledger time keys (`BackfillLedgerTimes`). All use bounded transactions and durable ID cursors; malformed rows fail closed without stalling later rows.
2. **journal summaries** (1 s gap, 16 actors per cycle) — `actor.AdvancePendingJournalSummaries` derives the v23 journal-summary state. A failing actor is skipped and retried on the next lap rather than blocking every actor behind it (it used to leave them all pending at probe score 0).
3. **campaigns** (optional: never affects readiness) — `campaign.Worker.Tick` via `runOptionalWorker`: takes the cross-process worker lease, then records evidence, settles scripts, assigns families, regroups, prunes. A failing tick backs off, **keeps reporting its error on every tick of the backoff window** (`Tick` returns the retained error, so `/metrics` `worker_error{worker="campaigns"}` stays 1 and `last_success` stale until a real success — returning nil from the no-op ticks made a permanently failing worker read healthy >99% of the time) and is logged once per streak by `runOptionalWorker` (first failure, each change of text, recovery), but never turns `/readyz` red: campaigns are derived analysis, and a regrouping bug must not take down the collector. See Campaigns and scripts.

**Only under `live`** (up to five more):

4. **cowrie ticker** (5s default, `--interval`) — `cowrie.IngestFileAppend` + `capture.Runner.Run`.
5. **capture file worker** (only with `capture.enabled`) — `capture.FileWorker.Run`, the v24 durable file-capture jobs; polls every 1 s, 10 ms while a tick found work.
6. **artifact retry worker** (only with `capture.enabled` and `capture.quarantine_fetch`; 10s poll) — `capture.ArtifactWorker.Run`, retrying failed quarantine fetches with lease-based claiming and a 5-attempt budget (schema v17).
7. **journal tail** — `journal.TailFollowObserved` in a restart loop that waits 1 s and re-reads the last 5 minutes after each stop (journalctl -f never self-exits; a scanner error would otherwise silently kill ingest for the process lifetime). Started unless `--no-journal`; every other `live` worker is gated only by the capture config above.
8. **purge loop** (once at startup, then every 24h) — `store.MaintenancePurgeContext` + `PurgeOldSourceFilesContext`.

### Ingest (`internal/ingest/{cowrie,journal}`)
Both sources: parse text → `[]*models.Event` → assign actor IDs → persist. Two modes per source: full-replace (`IngestFile`, `--replace`) and incremental append (dedup-based, used live).

- **Incremental Cowrie ingest is genuinely O(new bytes)**, not O(file size). `IngestFileAppend` persists `IngestState{Inode, Offset, HeadSig}` and seeks to the offset. Rotation is detected three ways: inode change, size < offset (truncate), and a sha256 of the first 512 bytes (catches copytruncate — same inode, replaced content). Offset advances by bytes *actually consumed*, never `fi.Size()` (Cowrie may append mid-Stat). Uses a bounded line reader (not `bufio.Scanner`) so one >2MB attacker line is skipped-but-consumed rather than wedging ingest forever.
- **HASSH stamping is essential** (`stampHASSH`, `persistBindings`): Cowrie emits the HASSH fingerprint only on `cowrie.client.kex`, which isn't a persisted event. Ingest extracts session→hassh bindings as a side channel and back-fills `e.HASSH` onto each session's real events. Without this, every Cowrie actor would cluster by IP, defeating the fingerprint premise.
- Shared dedup (`store/events_dedup.go` `IterateEventIdentitiesByTS`) has a load-bearing SQLite-planner workaround: it filters `WHERE ts IN (...)` only and re-applies the `source` filter in Go, because *any* `source=` predicate makes the planner do a full-source scan. Don't "simplify" it back into SQL.

### Actor model (`internal/actor`)
An actor is a **clustered attacker identity, not one-per-IP**:
- `journal:<src_ip>` — clustered by IP (their attempted-username distribution is their personality).
- `cowrie:<hassh>` — clustered by HASSH (one HASSH across 3 IPs = one actor); falls back to `cowrie:<src_ip>` when HASSH is absent.
- **Admin IPs are excluded from all clustering** (`AdminSet` → `netmatch.Set`, accepts IPs + CIDR like Tailscale `100.64.0.0/10`) so you don't classify yourself as an attacker.
- `playbook.go` labels behavior (`fast_dictionary_spray`, `crypto_target`, etc.) from username taste × attempt rate; `ProbeScore` (0–100) and `Confidence` (fixed tiers) feed dashboard sort + report vetting.
- **Two labels cover the connect-only majority**: `handshake_scan` (connected, never authenticated) and `scanner_tool` (authenticated but no credential *taste* to profile). Before they existed 74% of live actors sat at `unknown`; they are 96% of cowrie actors on prod. Neither ends in `_spray`/`_enum`, so `abuseipdb.Vet` refuses them for free — a scanner can never be reported as a brute-forcer. Don't "simplify" the suffix check into an allow-list that would have to be updated for every new label.
- `actors.flags` (schema v18, `models.ActorFlag*`) persists the event-mix bitmask so ingest folds fresh events into the stored aggregate instead of re-scanning the actor's whole history — this is what took the live daemon from 22% CPU to 2%. Rows written before v18 carry `flags=0` and are repaired by a one-shot full re-scan on their next touch; `reclassify` does the same. An actor whose events retention already purged can never be rebuilt (no data) — `planReclassify` counts those as `Unrebuildable` rather than silently skipping them, and `MaintenancePurge` now deletes them outright (see Store).

### Store (`internal/store`, largest package — SQLite via `modernc.org/sqlite`)
- **Writes are serialized at the app layer by a single `writeMu`** (`WithTx`/`execWrite`), *not* by a 1-connection pool. The pool is 8 connections in WAL mode so reads stay parallel with the single writer. Every write goroutine (journal tail, cowrie ticker, capture workers, purge, backfills, campaigns, web) goes through `writeMu`. The DB file is chmod 0600 (it holds attacker passwords).
- **Migrations** are a linear ladder v1→v26 in `sqlite.go`, each guarded `if current < N` and stamped `INSERT OR IGNORE` into `schema_migrations`. A base `CREATE TABLE IF NOT EXISTS` block runs first; old DBs get guarded `ALTER TABLE ADD COLUMN` steps. **Most migrations are index tuning driven by EXPLAIN QUERY PLAN** — read the comments before touching them (e.g. v9 *drops* a write-amplifying index; v10 replaces `idx_events_actor` with composite `(actor_id, ts)`). The feature tail is v16 session side channels, v17 artifact retry state, v18 actor flags, v19 capture evidence timestamps/leases, v20 `events.ts_unix_ns`, v21 a partial index of unconverted event timestamps, v22 canonical time keys for the three submission ledgers (with triggers that invalidate a key when an old writer changes the raw time), v23 durable journal-summary derivation state (pre-v23 profiles read as `unknown_history`, never certified from retained subtotals), v24 durable file-capture jobs (fenced leases, so every Cowrie download is archived rather than the newest 200), and v25 campaigns and script fingerprints (per-session evidence and settled scripts with `scripts.token_count` for family preselection, persisted campaign identity, and an index on `campaign_edits(campaign_id)`; see Campaigns and scripts), and v26 the `script_version_carry` table plus three partial indexes over command-bearing events (`idx_events_actor_cmd (actor_id, ts)` and `idx_events_cmd_ts (ts)`, both `WHERE command IS NOT NULL AND command != ''`, and `idx_events_actor_cmd_legacy (actor_id, ts)`, which adds `AND ts_unix_ns IS NULL` so the per-actor legacy branch is bounded by unconverted rows and empties as the backfill runs) for the `/api/intel` last-command and recent-commands reads and the shell-session candidates: `idx_events_actor_ts` cannot skip the ~99% of rows with no command, so an actor with none (most handshake scanners) was walked end to end, and partial indexes charge only the ~1% of inserts that carry a command, so the v9 write-amplification lesson still holds. The index `WHERE` must stay character-for-character the queries' predicate or the planner cannot use it (the queries name it with `INDEXED BY`, so a mismatch errors rather than degrades; `shellCandidates` once spelled it `COALESCE(command,'')<>''` and walked every in-window event). **v26 creates `script_version_carry` because v25 was released without it**: the campaigns rc1 stamped production at 25, the table was appended to the v25 DDL afterwards, and `migrateCampaigns` runs only below 25, so rc2's first campaign tick died on `no such table` while `/metrics` read healthy. The DDL is `scriptVersionCarrySchema`, shared by the v25 constant (fresh databases) and the v26 rung (`IF NOT EXISTS`, every database already at 25). **Never amend a shipped rung's DDL — add the object to the next rung**, and `released_schema_test.go` enforces it: it keeps the `sqlite_master` of the shipped v24 (v2.8.0) and v25 (rc1) as `testdata/` fixtures dumped from those builds, opens each with the current store, demands the **full definition** of every object a fresh database has — each index's and trigger's `sqlite_master.sql` (whitespace and comments normalised) and each column's `(type, notnull, default, pk)` — and runs the first worker tick's store calls on an rc1 database holding settled scripts (the rc1 script row must move to the new fingerprint with its ID and seq, and the campaign name must survive). It compared names only before, so an index whose `WHERE` drifted from the queries' predicate passed; a table's own `CREATE` text is deliberately not compared, because `ALTER ADD COLUMN` rewrites it and `PRAGMA table_info` is what the reads depend on. **The v26 objects are self-healing** (`v26Objects`, `healV26Objects`, run after the ladder on every `Open`): the unreleased rung was amended in place four times (09cf7fd, 7067d76, 90140fa, 1c69a01), so a database an intermediate build stamped 26 (a dev copy, the benchmark DB, a rehearsal restore) never re-ran `current < 26` and answered every `/api/intel` with `no such index` (the reads use `INDEXED BY`). The heal first counts the objects in `sqlite_master` without a lock, so a healthy database takes no `writeMu` and no write lock at `Open` (a `web` beside a busy `live` must not queue behind it); only a database missing one runs the `IF NOT EXISTS` DDL, once. The stamp stays 26 — a v27 rung repeating the DDL would only move the same trap to whichever build shipped it; `TestIntermediateV26DatabaseHeals` reopens each intermediate shape. v20 is schema-only during `Open`; long-running web/live modes backfill legacy rows in bounded transactions so startup never rewrites the events table. Mixed event readers merge the normal timestamp indexes with an exact RFC3339 parser over that shrinking legacy index; avoid millisecond buckets, whole-window Go buffers, or forcing the global legacy index on actor-specific reads. To add schema: append the next version and update this figure.
- Lazy tables (artifacts, ip_enrichment, bazaar_uploads, session_hassh, abuseipdb_reports…) are each created on first use via a `sync.Once` to avoid DDL under `writeMu` on hot calls. When batching writes across several of these in one `WithTx`, call the `ensure*` helpers **before** opening the transaction — they take `writeMu` via `execWrite`, and `writeMu` is not reentrant, so ensuring inside the tx deadlocks (see `RecordSessionBindings`).
- `MaintenancePurge(retentionDays)` deletes events in **5000-row chunks, each its own transaction**, releasing `writeMu` between chunks so a first purge of an aged DB doesn't stall ingest for minutes; then unlinks the corresponding evidence files and runs `PRAGMA optimize` (also run once at `Open` after migrate) so the plan-sensitive queries keep their intended index plans as cardinality shifts. It then sweeps **orphan actors** — rows whose every event the purge just deleted. Actors are derived data; an orphan keeps a stale `event_count` and a playbook frozen at whatever the classifier last said, inflates the dashboard's actor count, and can never be reclassified because there is nothing left to re-scan (prod carried 103 such rows, 102 reading `unknown` — the entire residual unknown population). Three guards make it safe and **all three are load-bearing**: `last_seen < cutoff` (so the ingest tick's just-created actor is never raced away), no surviving events, and no operator annotation (`campaigns`/`notes` are human work and deliberately outlive the telemetry). Unlike events it is one transaction, not chunked — actors is bounded by distinct attacker identities, thousands against a million events.
- **Windowed reads for the UI are bounded.** `EventsSinceCapped(since, limit)` returns at most `limit` (default `defaultWindowEventCap`) newest-first events **plus the true window total**, so callers disclose "N of M" instead of materializing a whole 30d window into RAM. `EventsSinceAll` (uncapped) still exists for non-UI use but shouldn't be reached from a poll path — prefer the capped form.

### Geolocation (`internal/web/geo.go` + `geo_mmdb.go`) — two tiers, local first
`mmdbResolver` (MaxMind GeoLite2/GeoIP2 City, path from `geoip.mmdb` or `SHARDLURE_GEO_MMDB`) is **tier 1**; ip-api.com HTTP is tier 2 and only consulted for IPs the database can't answer. Three reasons this matters, all measured on the live deployment: (1) **coverage** — `prefetch` caps the HTTP tier at 48 IPs/call plus a wall-clock budget and only resolves IPs currently on screen, which left ~77% of attacker IPs permanently unresolved; the MMDB sweep in `prefetch` deliberately **bypasses that cap** because memory-mapped reads have no quota. (2) **privacy** — the free ip-api tier is *plain HTTP*, so every attacker IP was disclosed in cleartext, contradicting the no-leak discipline in bazaar/abuseipdb. (3) **air-gap** — completes the story started by vendoring the globe engine. A configured MMDB makes `isEnabled()` true on its own, so geo works with `geo.http` off entirely (zero-egress config); `httpTierEnabled()` is the separate gate for outbound. A missing/corrupt database is **fail-open** (logs, degrades to HTTP, reports via the Settings badge), matching the keyless enrichment providers. Opened once at startup — it backs an mmap that can't be swapped under concurrent readers, which is why the path is *not* a live keystore setting.

### Enrichment (`internal/intel/enrich`) — inbound IP reputation
Seven providers (AbuseIPDB, VirusTotal, GreyNoise, Shodan, AlienVault OTX, IPQualityScore, IPinfo; GreyNoise + Shodan work keyless). Each is a `providerSpec{envVar, keyOptional, buildReq, parse, notFound}` — **adding provider #8 is one file + one row in the `providers` slice** (a `[]provider`, each pairing a `Provider*` id with its spec). `LookupAll` gates every IP through `safeForEnrichment` (rejects private/reserved — SSRF defense) then fans out 7 goroutines into fixed slice indices (stable order), each with a 6s timeout. Cache-then-fetch with 24h TTL; only caches `Configured && Error==""` results so adding a key takes effect immediately.

### Outbound intel (`internal/intel/{bazaar,urlhaus,threatfox,abuseipdb,ioc}`) — the vetting-gate pattern
Each has a single `Vet`/`vet.go` function that **both the CLI and the dashboard call** — policy lives in exactly one place, and **hard-rejects always win over accept signals**. Candidate structs deliberately omit any host/session identifier so nothing leaks to third parties.
- `bazaar` — uploads confirmed-malware payloads to MalwareBazaar; `Vet` enforces abuse.ch policy (no tty transcripts, no SSH keys, ≤10 days old, confirmed-malware OR fetched-during-attacker-session). **Candidate selection must never be tighter than `Vet`** — a sample dropped before the gate is rejected by an invisible second policy with no reason an operator can read. `Vet` therefore exports `MinSampleBytes` (64) and `ShareableOrigins()`, and `store.ArtifactsForShare`/`ListArtifactsAggregatedSince`/`PayloadShareable` take a `store.SharePolicy` built from them (passed in, not imported — `store` must not depend on `intel/bazaar`). The pre-filter drifted twice and each drift silently hid real payloads: `origin LIKE '%download%'` excluded `quarantine_fetch`, the capture runner's own fetches (10 payloads, 18.6 MB), and `size_bytes > 1024` sat 16× above Vet's floor (13 dropper scripts). A zero-value `SharePolicy` marks **nothing** shareable, so a forgotten argument fails closed. The dashboard's **pending stat counts under the same policy + freshness window** (`BazaarUploadStats(since, pol)`) — it kept a private legacy filter after the selection fix and claimed 148 pending against a real pool of 30. Relatedly, **shareability is a property of the sha group, not of the newest row** (67 prod hashes mix origins — same payload recorded by both the cowrie hook and our fetch, and a newer row can be a *failed* re-fetch): the server answers it group-level and the dashboard consumes that flag instead of re-deriving it from `origin` in JS, which is what cost two family-identified droppers their share button while the CLI was selecting them. `--limit` bounds **submissions inside `Share`, after `Vet`** — truncating the candidate slice first spent the whole budget on already-shared hashes at the top of the newest-first list and uploaded nothing. Every local skip reports through `OnProgress`; a bumped `skipped` counter with no per-sample line is unreadable. Family attribution is `elf_family.go` — **precision-first Tier-A anchors** (plus XOR-decoded config/credential tables and UPX detection), shared with `threatfox`'s Malpedia gate. It deliberately yields *no* family rather than a guess: on the live corpus that means scripts resolve (`redtail`, `Coinminer`, `Traffmonetizer`) while packed and Go-built ELFs stay unnamed. That is the design, not a gap — a wrong `malware` label is what gets the shared abuse.ch account banned. **A truncated or malformed ELF still gets the family scan**: when `elf.NewFile` fails (a download cut short — Cowrie does capture partial downloads — or a mangled section table) `classifyELF` loses only the arch/`static` tags and the structural packing checks; the Tier-A head scan and the byte-level packing checks run on any head. It used to return early, so a truncated XMRig carried no family and the campaign worker's generic-build exclusion, which keys on that family, let it link. The anchors are the same evidence that names the whole file, so the family is reported, not withheld.
- `abuseipdb` — reports confirmed brute-forcers; `Vet` requires `_spray`/`_enum` playbook AND ProbeScore ≥ floor AND ≥20 events AND ≥3 users, excludes admin/private IPs (account-strike defense), and hard-rejects anything **last seen more than 7 days ago or carrying no timestamp at all** — a report asserts present-tense abuse, and the suggestions widget was offering IPs dormant 31–50 days because `ReportCandidate` had no date for the gate to read. Staleness is checked *before* the accept signals, so probe 100 and six-figure event counts cannot carry a dormant IP through. Tightenable via `VetOptions.MaxAgeDays` (1..6), never loosenable, exactly like `bazaar.FreshnessDays`/`urlhaus.ActiveDays`. `store.ReportPoolMaxAge` bounds the pool query to match; the pool is an optimisation, `Vet` is the policy. `--limit` bounds **reports inside `Report`, after `Vet` and dedup** (`Options.MaxReports`) — the same fix as `bazaar`'s `MaxUploads`, and for the same reason: candidates are ordered worst-offender-first, which on any deployment with history is also already-reported-first, so truncating the slice first spent the budget inside the re-report window and reported nobody. **The candidate's `LastSeen` must be the primary IP's own observation (`store.PrimaryIPLastSeen`, from `actor_ips`), never `actor.LastSeen`** — the actor figure is the max across a HASSH cluster, and a 4-day-old cluster-mate carried a 17.7-day-dormant primary IP through the gate on prod. Missing map entry = zero time = Vet-rejected, so absent data refuses rather than reports.
- `urlhaus` — submits the malware-distribution **URLs** the payloads came from (bazaar ships the files). `Vet` requires a real `http(s)` URL (this is what rejects the capture runner's `cowrie-download:`/`cowrie-event:` dedup pseudo-keys), `origin=quarantine_fetch` + `status=fetched` + a payload hash ≥ 64 B (first-hand proof the URL served something), a public IP/hostname (RFC1597/6890 is an explicit policy requirement), no shorteners, and a fetch inside `active_days` (default 3, may only tighten). `urlhaus_submissions` is a dedup ledger and is **never purged**; the SQL in `store.URLhausCandidates` must stay identical to the Pending subquery in `URLhausSubmissionStats` (they drifted once and the UI count disagreed with the CLI's list). `--limit` bounds **submissions inside `Share`, after `Vet` and dedup** (`Options.MaxSubmissions`) — it was a SQL `LIMIT` on the candidate query, the same pre-gate truncation as the bazaar/abuseipdb twins in different syntax; the CLI now collects unbounded (`URLhausCandidates(activeDays, 0)`). Surfaced on the **Blue Team** tab (`panel-urlhaus`) — the panel renders `Vet`'s per-candidate decision *including the rejection reason*, and `handleURLhausSubmit` re-runs the gate server-side so the button (and a hand-crafted `?url=`) can never bypass policy; `urlhausBatchMu` stops a double-click racing the ledger.

- `threatfox` — submits the malware-delivery **IOCs** (url + host `ip:port`/`domain` + sha256) for payloads ShardLure fetched first-hand, the third abuse.ch give-back on the same key. `Vet` is the urlhaus gate plus **one hard extra: the classifier's family must resolve to a real Malpedia label** (`internal/intel/threatfox/malpedia.go` — only `mirai→elf.mirai`, `gafgyt→elf.bashlite`, `redtail→elf.redtail`, `xmrig→elf.xmrig`, each verified against the live `malware_list`; every other family is unsubmittable, never guessed — a wrong `malware` label is exactly the junk that bans the shared account). Host classification is shared with urlhaus via `intelutil.PublicHostKind`/`HostNormalise` (the two gates MUST agree on "public payload host"; extracted so they can't drift). **IPv6 hosts must go through `net.JoinHostPort`** — the naive `host+":"+port` renders the malformed `2606::1111:80` (found in adversarial review). `submit_ioc` responses: `ok`/`duplicated` arrays = success (record in the never-purged `threatfox_submissions` ledger), `ignored` or any non-`ok` `query_status` = failure (do NOT record, so a fixed run retries). `--limit` bounds submissions inside `Share` (`Options.MaxSubmissions`, counts candidates, dedups per-IOC); `store.ThreatFoxCandidates` SQL == `threatfoxPendingSQL`. Blue Team `panel-threatfox`, server-side re-vet in `handleThreatFoxSubmit`, `threatfoxBatchMu`.

**The one-key invariant.** abuse.ch issues a single Auth-Key per account covering MalwareBazaar, URLhaus *and* ThreatFox. There is exactly one resolution path on each side — `web.abuseCHKeyLive()` (with `bazaarKeyLive()` as a thin alias) and `cmd.abuseCHKey()` — both DB > env > config. Deliberately **no `urlhaus`/`threatfox` key setting exists** in the keystore registry: a second field would let them silently drift and half-arm sharing.

**CLI subcommands must read the keystore, not config/env.** `main.go` seeds the keystore *from* config at startup, never the reverse — so a value saved in the dashboard Settings panel exists **only** in `app_settings`. Every outbound CLI path therefore takes `*settings.Keystore` and resolves DB > env > config: `share bazaar` / `share urlhaus` via `abuseCHKey()`, `report abuseipdb` via `resolveAbuseSettings()`. This bit three times before it was fixed everywhere — and for AbuseIPDB it was not just the key: the **enable flag, categories, comment, min-probe and rewindow** were all config-only, so a dashboard-configured deployment got a CLI that refused to run ("report_enabled is false") and would have reported with the wrong policy. `resolveAbuseSettings` mirrors the server's `abuse*Live()` accessors one-for-one; flag defaults are seeded from it so an explicit flag still wins.
- `ioc` — emits **byte-stable** STIX 2.1 (deterministic UUIDv5 IDs) so re-exports diff cleanly.

### Payload hash intel (`internal/intel/vt`) — quota-shaped, not poll-shaped
VirusTotal's **file** endpoint (distinct from the IP provider in `intel/enrich`). The free tier is ~4 req/min, which dictates the whole design: lookups are **on-demand only** (never a background sweep), verdicts cache in `payload_intel` for 30d (7d for not-found) because a file hash is immutable, concurrent lookups of one hash collapse via a `sync.Map` of `sync.Once`, and errors/429s are **never cached** (a transient rate-limit must not blank a verdict for the TTL — a stale cached value is returned instead). HTTP 404 is a first-class `found:false` result, not an error. Two endpoints by design: `/api/intel/payload/vt` spends quota; `/api/intel/payloads/vt/cached` is cache-only and safe for list renders. Only the sha256 is transmitted — the file is never uploaded.

### Settings keystore (`internal/settings/keystore.go`)
Leaf package (imports only `store` + stdlib). Precedence on read: **DB value → env var (`SHARDLURE_*` only) → ""**. API keys and knobs (`ui.theme`, `abuseipdb.*`, `home.*`) live in the `app_settings` table, read **live at request time**, so a dashboard Settings save takes effect **without restart**. `main.go` seeds it from config/env at startup so existing systemd deployments are unaffected.

### Capture (`internal/capture`)
Every 5s: extracts URLs from recent commands and quarantine-fetches them, syncs Cowrie's downloads + ttylogs into `evidence/{quarantine,cowrie,cowrie-tty,meta}` (0700/0600). **`SafeFetcher` is SSRF-hardened**: `safeDial` re-resolves DNS and validates the actual IP *at dial time* (closes the resolve→connect TOCTOU / DNS-rebinding hole), size-caps downloads, and **never executes content**. Dedup memos skip the copy+hash *before* the dedup query to avoid GB/min write amplification.

### Campaigns and scripts (`internal/script`, `internal/campaign`)
Groups activity that is very likely one operator and shows the evidence for every link. Local investigation only: campaigns are never exported or shared. (The design spec, `.superpowers/specs/2026-09-28-campaigns-and-scripts-design.md`, is a local planning document and is not tracked; this section is the durable record.)

- **Sessions are the nodes, not actors.** A HASSH is a client-library fingerprint, and one HASSH cluster can hold several tools: on prod a Go/OpenSSH HASSH actor ran an unrelated `echo SHELL_TEST` scanner and the Outlaw key injector. Unioning actors let that one actor bridge unrelated campaigns; unioning sessions that share a linking value does not. A campaign is a component whose sessions come from ≥2 distinct actors, and an actor can sit in several campaigns.
- **What links.** `ssh_key` (the `SHA256:` fingerprint of a key blob found in command text, identical to `ssh-keygen -l` for the keys it takes: `ExtractKeys` parses each type's wire fields to the end — mpints as OpenSSH reads them (non-negative, at most 2049 bytes, 2049 only with a leading zero), an RSA modulus of 1024–16384 bits, exactly 32 bytes for ed25519, an on-curve point for ecdsa/sk-ecdsa, no trailing bytes — because `ssh-ed25519` followed by garbage and a 63-bit RSA key used to be fingerprinted although `ssh-keygen` rejects them; RSA/DSA keys are hashed **re-encoded with minimal mpints** (`canonicalKey`), as `ssh-keygen` hashes the key it re-serialises, so a leading-zero variant gets `ssh-keygen`'s fingerprint instead of a second one; DSA has no size rule in OpenSSH 9.6, so only canonicalisation applies to it), `payload` (sha256 of a download/upload/redirect with a known size ≥ 64 B, not the empty file, not a generic public build — `genericFamilies`: `xmrig`, `coinminer` and `traffmonetizer`. Traffmonetizer is the vendor's public proxyware client, byte-identical for every operator who deploys it, so its hash names the vendor, not an operator; commonness catches such builds at scale, but on a small honeypot two unrelated operators sit below the ≥5-actor floor and became one campaign. The exclusion is by family label, so a dropper script the classifier names after the brand is excluded too, as xmrig/c3pool droppers already were; such a session still links through its script and any key it injected), and a settled `script` that passes `script.LinkDecision` (≥5 simple commands, at least one non-recon program or a `<key>`/`<url>`). HASSH, client version and payload host are context and never link. **Commonness** applies to all three: a value used by >25 distinct actors, or by ≥5 actors that are also >2% of the Cowrie actor population *within the retention window*, is shown as context and never links. The ≥5 floor keeps a small honeypot, where two actors are already several percent, from calling every shared value common; mismatched populations (all-time actors against windowed values) were a review finding.
- **Scripts settle once.** Commands are stored append-only per event (keyed by event id, so replay is idempotent). A session's script is fingerprinted (SHA-256 of the `\x1f`/`\x1e` encoding) only after it has been idle 10 minutes on **both** clocks — event time (`last_seen`) and ingest time (`updated_at`). Without the second, the history seed would fingerprint a session's prefix before the rest of its old events were recorded; no prefix rows are ever written. Late commands re-settle the session and `PruneOrphanScripts` removes the stale row: the recorder's upsert sets `settled_at=''` whenever it adds lines, an explicit dirty flag, because judging "changed since settle" by `updated_at > settled_at` alone missed a late line after a wall-clock correction (a settle while the clock ran ahead left `settled_at` in the future, so the later line's `updated_at` sat below it and the session kept its prefix fingerprint forever). Caps are 300 commands and 64 KiB of normalised text per session; the byte cap is `len(script.Join(lines))` and so counts the `\x1e` separators, which keeps the stored encoding itself, not just the command text, inside 64 KiB. **The script is the true capped prefix:** the first line refused for bytes **closes** the session (stored `bytes` becomes exactly `MaxNormalizedBytes`, which every later window and `sessionAtCap` read as full), and a session whose very first line is refused gets a settled 0-line row with no fingerprint. Before, a refused line only skipped itself, so shorter later lines were admitted and the stored script was not a prefix of what the attacker typed; a line whose *encoding* outgrows the cap (30,000 quoted `<` → 120,007 bytes) is the reachable case, since ingest caps raw command text at 64 KiB. Variant **families** are display only (never link): token Damerau-Levenshtein against family representatives, no chaining, joined at ≤0.12. The representative set is attacker-driven, so passes are bounded: representatives are listed by `(fingerprint, token_count)` and a representative's text is loaded only when its `token_count` falls in the 0.8 length-ratio band of some pending script, each pending script is compared with at most the **256 nearest in-band representatives by `token_count`** (`familyNearestReps`, ties by fingerprint, so a budget-split pass resumes to the same result; 3,000 in-band representatives cost 2.7 s per script before the cap, 0.24 s after), and distance work stops after a 2 s `familyPassBudget` (the rest resumes next pass in the same order). `RebuildScriptFamilies` (after each regroup) reads the stored `script_families` rows in the same read-only snapshot as the computed ones, diffs them **outside `writeMu`** and writes only new, changed or vanished families, in 500-row transactions (`familyWriteChunk`): it used to delete and reinsert every family under the lock on every regroup, while between two regroups only a handful change (an unchanged rebuild of 10,000 families is now 290–340 ms of reads and zero `writeMu`). Only the lease-holding worker writes that table, so the snapshot cannot go stale before the write. A representative whose own sessions retention took **dissolves its family** (`PruneOrphanScripts`: members' `family` cleared, distance 0, representative deleted, the next assign pass regroups them around a live one); it used to outlive retention indefinitely as long as members pointed at it. Re-electing a member in place was rejected: every other member's distance is measured to the old representative, and recomputing it needs `script.*` under `writeMu`. The **script dialog** (`GET /api/intel/script`) carries the family block — `variants` (each fingerprint with its session count, capped at `scriptVariantCap` with `variantsTotal`; see Persistence), `familySessions`/`familyActors`/`familyIps` and `sessionsTotal` — so it reads "this variant: N of M family sessions" and every variant opens through its fingerprint (the palette searches variant fingerprints too). Before, the Scripts row counted the whole family but the dialog listed only the representative's sessions and other variants could not be opened. The family comes from a bounded `ListScriptFamilies(1000)` scan at dialog open (never on a poll); a family outside the top 1000, or a failed lookup, only omits the block.
- **Normaliser rules (`internal/script/normalize.go`).** Program detection decides `Distinctive`, so each of these once let a recon script link or hid a real program. Wrapper options keep the program (`nice -n 5 python3`, `sudo -u root`/`sudo -s`, `timeout 30`, `env A=1`, `stdbuf -oL`, `nohup`): each wrapper lists its flags and value-taking options, and an **unknown option stops wrapper parsing and reports the wrapper itself** rather than guessing which later word is the program. Attacker-typed `<` and `>` inside a quoted word encode as `<lt>`/`<gt>`, so a literal `"<url>"` can neither count as the normaliser's own placeholder nor share a fingerprint with a real URL (`\<url>` was rejected: `"\http://x"` already normalises to it); `Display` renders them `\<`/`\>`. A leading redirection, heredoc or here-string keeps the program slot open (`> /tmp/a python3`, `<<EOF python3`, `<<< x python3`), a redirection target keeps a following `$(…)` group (`> $(evil) python3` runs python3, not evil; `groupEnd`, shared by `NormalizeCommand` and `program()` so the two agree), and a bare `>&`/`<&` is one redirection token taking the next word (`takesTarget`), while `2>&1`, `<&3`, `2>&-` carry their target. `command`, `type` and `hash` are recon (tool probes). **Tokenising is a hand-written, resumable `scanner` that reads bash word syntax** (Version 5, each rule checked against bash 5.2), not a regex: a heredoc body has to be cut out of the source by whole lines and tokenising resumed after its terminator, or a quote inside the body pairs with one after it; re-running a regex after every body would be quadratic. The rules: blanks are space and tab; a backslash-newline outside quotes is removed everywhere, operators included (`>\⏎>` is `>>`); an unquoted `#` at a word start is a comment that yields no token, so a shebang line is no program; `\` escapes the next byte, `'…'` is literal, and `"…"` ends only at an unescaped `"` (inside it `\` escapes only `` $ ` " \ `` and newline); quotes may start mid-word; `` `…` ``, `$'…'`, `$"…"` and `${…}` are read whole, and so is a `$(…)` inside double quotes (its content is tokenised like the top level, heredocs and comments included); an unquoted `$(…)` still tokenises as `$ ( … )`. A word keeps its quotes and escapes, so `echo "\"   x"` and `echo "\" x"` no longer collide. Each of these once hid a real command or linked a recon script: under Version 4 `echo A \<<EOF⏎python3 x⏎EOF⏎perl y` hid `python3`, a comment containing `<<EOF` or `'` swallowed the rest of the script, and `#!/bin/sh` made `sh` a program and a five-command recon script Distinctive. A top-level opener that never closes is an ordinary byte (a stray quote cannot hide later commands); inside a substitution a failure propagates, as in bash. Every construct's end is memoised per opening position (`scanner.spans`), so the pass stays linear on every measured hostile shape — the worst at 64 KiB is ~63 ms; the first Version 5 draft read a failed nested construct as bytes and rescanned it, and 64k `(` took 7.5 s at 16 KiB. `tokenRe` in `normalize_test.go` is the specification for inputs without nesting (`tokenSpecCovers`: no backtick, no `${`, no `$(` beside a `"`), and `TestScannerMatchesTokenRe` plus `FuzzNormalizeCommand` require the scanner to agree with it there; the nested forms were checked by a bash `extdebug` DEBUG-trap differential (Version 4 had 15 hidden commands in 12,000 random scripts, Version 5 has 0 in 20,000) and are pinned by `TestBashWordSyntax`. **Heredocs are bash-exact**: `scanner.delimiter()` reads the word after `<<` straight from the source with bash's quote removal, keeps `$(…)`, `` `…` ``, `${…}` and `$((…))` literally (`<<$(x)` ends on a `$(x)` line; its paren used to end the word, so no line matched), decodes `$'…'` as bash 5.2 does (`ansiDecode`: `\c?` is DEL, `\c\\` spans both backslashes, a NUL ends the string, bash's up-to-6-byte UTF-8 for `\u`/`\U`), and a construct left open is not a heredoc. `skipBodies` ends a body only on a **whole source line** equal to the delimiter (leading tabs stripped for `<<-`), in order for several heredocs on one line, running to the end of the command when unterminated; an **unquoted** body joins backslash-continued lines before matching (`E\`+`OF` terminates, `x\`+`EOF` does not). Trimming only the outer quotes left `<<\EOF`, `<<E"OF"` and `<<"E O F"` unmatched, so the body swallowed **every later command** and different droppers collided; an indented `  EOF` no longer ends a body (bash does not either), and `<<` followed by an operator (`cat << ; id`) is not a heredoc. **A quoted delimiter's placeholder is `<heredoc-q>`** (`heredocQTok`): bash runs a `$(…)` in an unquoted body and not in a quoted one, and both used to encode as `<heredoc>`. **Control bytes**: `\r`, `\f` and the separator bytes are word bytes (`\x1f`/`\x1e` encode as `<us>`/`<rs>`; stripping them to blanks made `wget\rhttp://…` and `wget http://…` collide), and only an **all-CRLF** event has its line endings read as LF (`crlfToLF`), so `EOF\r` does not end an LF-opened heredoc (bash keeps reading the body there too). **An arithmetic `(( ))` runs no program** (`((` is in `noProgram`; the scanner emits it only when bash would read arithmetic, so `((id); w)` stays two subshells), and `[`, `test`, `:`, `true`, `false` and `sleep` are recon — `(( i++ ))` used to be program `i++` and `[ -d /tmp ]` program `[`, each making recon Distinctive. `program()` applies bash quote removal (`dequote`), so `\id`, `'id'` and `"i"d` are all `id`. **Heredoc bodies are fingerprinted**: the body follows the placeholder inside the same token (`<heredoc><nl>line1<nl>line2`, each line normalised like quoted text), so it adds no commands and never becomes the program; dropping bodies gave two different `cat > /tmp/x <<EOF … EOF; sh /tmp/x` droppers one fingerprint and linked them. A body is bounded at `MaxHeredocBodyBytes` (4 KiB raw, cut on a rune boundary and marked `<nl><more>`) so a payload-sized heredoc cannot push its line past the 64 KiB session cap, which would refuse the line and, with it, the rest of the script; a `<url>`/`<key>` in a body counts toward `Distinctive`, like the `echo "…" > f` form, and `Display` renders `<nl>` as `\n`. **Shell syntax is never a program**: `program()` skips the reserved words `if then else elif fi do done while until esac { } ! ]]` and keeps the slot open after them (`if python3 x` → `python3`), and a segment led by `for`, `case`, `select`, `[[` or `function` has no program; `N<file`, `N<>`, `N>|` and fd-prefixed heredocs/here-strings (`0<<EOF`, `2<<<x`) are redirections and never take the program slot. Heredoc delimiters are read as one bash word with bash's quoting (`<<E"O F"`, `<<E\ OF` end where bash ends them; each case checked against bash 5.2), and an unclosed quote is not read as a heredoc, so no later command can be hidden behind a delimiter the parser misreads. Before, `{ w uname uptime }`, `0</dev/null …` (program `<n>`) and `>|` made recon-only scripts Distinctive. **A quoted program name keeps its name** (`quotedBare`: `'id'`, `"wget"`), where it used to become `<tok>`, so `'id'; "uname" -a` read as Distinctive and `"wget" x`/`"curl" x` collided. **URLs, IPs and `/tmp` names stop at a backtick**, or `` `wget http://x/y` `` encoded like its unclosed form. **Quoted text** also replaces hex runs of ≥ 16 with `<hex>` and numbers of ≥ 6 digits with `<n>` (the floor keeps ports and modes like `8080`, `777`; before, `echo "root:123456789" | chpasswd` kept the password), and a real newline or carriage return inside a word encodes as `<nl>`/`<cr>` (not `\n`/`\r`, which a typed `\n` also produced; an attacker's `<` is escaped, so the placeholders cannot be forged). **Accepted residual limits** — each can cost a link, never create a false one, and the fingerprint stays deterministic: **programs inside `$(…)` and backticks are not fingerprinted**, apart from a program leading an unquoted `$(…)` (`$(python3 x)` gives `python3`), which the `$ ( … )` token model already exposes; backticks are one word, so nothing inside them is seen. Doing it properly needs a recursive program pass whose cost grows with nesting depth (the scanner is linear only because each construct's end is memoised once), and bash runs a substitution's *output* as the command, so what the script names is not the program anyway. Also accepted: an operator inside an unquoted `$(…)` still splits the command there; text glued to a closing `)` (`> $(evil)x python3`) is read as a later word; and inside a double-quoted `$(…)`, a nested `case` pattern's `)` or a heredoc opened in a nested subshell can end the scan early (`parenEnd` skips a nested group whole).
- **`script.Version` and the rebuild.** Stored lines are pre-computed encodings, so **bump `script.Version` for any change that can alter an encoding or a settled value** (tokenising, placeholders, program detection, escaping, separators, the recon list, the heredoc body bound, `Tokens` and its cap — `scripts.token_count` is stored — the family constants, and `MaxCommands`/`MaxNormalizedBytes`, with which the store cuts a session's true capped prefix; not a refactor) and extend its history comment; otherwise old and new sessions of one script fingerprint differently forever. The current value is **5** (4 = the heredoc, syntax-word, quoted-name, backtick and quoted-number rules plus the store's true-capped-prefix change, which alters settled values; 5 = the bash word, comment and escape syntax, the heredoc delimiter/body/`<heredoc-q>` rules, control bytes, arithmetic and no-op recon, and `ExtractKeys`' ssh-keygen rules above). rc2 stamped 4 on prod, so the first Version 5 build runs one more rebuild. **`TestVersionPinsEncoding` (`version_test.go`) enforces the rule**: it hashes, for a hostile corpus, each encoding, `Display(…,120)`, `CommandCount`, `Distinctive` and `len(Tokens)`, the joined script's fingerprint, the token and family constants, `MaxCommands` and `MaxNormalizedBytes` (a `MaxCommands` 300→200 mutation used to pass the pin) and the recon, reserved-word, no-program and wrapper tables, and pins the digest to the Version (`versionPin`). **Any encoding change must bump `script.Version`, extend the history and update `versionPin` to the new Version and the digest the failure prints**; a bumped Version with a stale pin fails too. Never update only the digest. Once per process, before recording, the worker calls `store.ResetScriptsForVersion`, which compares it with `ingest_state(source='script_version', path='normaliser')` (a missing row counts as a mismatch). On a mismatch it snapshots each settled session's fingerprint into `script_version_carry` (created by the **v26** rung as well as the v25 DDL — rc1 shipped v25 without it, see Store), deletes `session_scripts` → `session_script_lines` → `scripts` → `script_families` in 5,000-row transactions (rows before lines, so a reader sees a session whole or gone; 300k lines reset in ~1.5 s with a 56 ms max `writeMu` hold on x86), then in one final transaction rewinds the recorder cursor to 0, sets `hold_hwm` = MAX(events.id) and writes the version last, so an interrupted reset reruns (`TestInterruptedResetStillCarries`: the rerun keeps every carry fingerprint because the snapshot is `INSERT OR IGNORE`). Before that final transaction it also deletes **`ssh_key` evidence** in 5,000-row chunks: `ExtractKeys` became stricter in Version 4 and again in 5 (which also hashes RSA/DSA keys re-encoded, so a leading-zero blob's value changes), so a row an older build wrote holds a value the current extractor never produces, and the rewind only ever re-adds rows. The valid keys come back identical on replay, and the hold keeps every regroup off until the recorder passes the mark, so their `campaign_ids` rows are never seen missing. Payload evidence (independent of the normaliser) and the identity tables are untouched. **Regroups are held** until the rebuild settles, because a regroup before the re-recorded sessions settle drops every script row from `campaign_ids` and the renamed campaign comes back under a new ID, its name and notes left on an empty shell. The hold is persisted (survives restarts), never ends while the cursor is below its recording target, and its 30 min `hold_deadline` is anchored **when the recorder catches up**, not at reset — anchored at reset, a restart after >30 min of downtime released it before anything was re-recorded. The recording target is `holdRecordTarget` = `min(hold_hwm, MAX(events.id))`, read by both `ScriptRebuildHold` and `ScriptRebuildHoldStatus`: the recorder stops at `MAX(id)`, so when the top of the id range was deleted after the reset (a journal `--replace` with an empty file, a purge of old-timestamped events ingested last) the cursor sat below the raw mark until a new event arrived — seconds under `live`, **forever** for a standalone `web` on a static database, with every regroup suspended. IDs are `AUTOINCREMENT`, so anything later lands above the raw mark anyway; the stored mark is not rewritten. It releases when every session with a line at or below the mark has settled, or at that deadline. While held, `Tick` does not regroup and does **not consume `Wake`** (the edit is recorded; the owed regroup runs on the first tick after release), and `Regroup()` returns `ErrRegroupHeld`. Release is one transaction that carries each old fingerprint's `campaign_ids` row to the new fingerprint holding **most** of its sessions (ties to the smallest fingerprint; nothing moves only when that winner is the old fingerprint itself); when several rows claim one target (a collapse), **the lowest `seq` wins**, then the lowest key. **Every Cowrie `--replace` arms the hold**, whether or not one is active: `clearCampaignDerivedTx` first snapshots each settled session's fingerprint into `script_version_carry` (`INSERT OR IGNORE`, so a hold already in progress keeps its older snapshot), then drops the deadline anchor and upserts `hold_hwm` to the `scriptHoldRemeasure` sentinel (-1), which the next check re-measures over the re-inserted rows. With a hold active, the parked cursor used to sit past `hold_hwm` and release it at once, dropping the carry; with none, nothing suppressed the drain's regroup, which ran before any re-recorded session had settled, replaced `campaign_ids` without the script rows and left the renamed campaign a named, empty shell (prod carries one). The re-ingested events keep their session IDs, so the release carries each row to whatever fingerprint its sessions settle to. The cost: after a `--replace` on a script-less database the first regroup waits for the settle (or the deadline) and carries nothing. **Release is a compare-and-swap on the mark** (`holdMarkUnchangedSQL`, bound to the `hold_hwm` value *and* the recorder's reset epoch read with it): the deadline write is `INSERT OR IGNORE … WHERE <predicate>`, and the release transaction starts with a conditional `DELETE` of the `hold_hwm` row and carries nothing when it affected no row, returning `held=true`. A `--replace` committed between the check's reads and its release used to release through it (the release deleted the replace's sentinel row and emptied its carry); the epoch also covers a second reset that re-measures the same mark. The **reset epoch** is the recorder cursor row's otherwise unused `inode` column, bumped by `rewindEvidenceCursorTx` on every reset or replace rewind (a fresh row starts at 1), never by ordinary recording; `RecordCampaignEvidence`'s phase 2 gives up (zero result, no error, retried next tick) when the cursor **or** the epoch moved since phase 1 — cursor equality alone was an ABA check, since a reset in another process can record back up to exactly the value phase 1 read, and phase 2 then wrote the old encoder's lines under the new version stamp. `ScriptRebuildHoldStatus` reads the hold without acting on it: `GET /api/intel/campaigns`, `GET /api/intel/scripts` and the edit response carry a `regroup` block (`held`, `phase` recording/settling, `progress`, `until`) and the UI explains the wait and parks its reload instead of saying "applying…" for ten minutes. The Scripts panel needs it most: the reset deletes `script_families` and only the first regroup after release rebuilds them, so for those 10–30 minutes the list is legitimately empty and the panel shows the rebuild note (meta line and empty row) instead of a blank table that reads as data loss.
- **Identity (`internal/campaign/group.go`).** Campaign IDs are persisted per linking value (`campaign_ids`), with losing IDs kept as `campaign_aliases`, so an ID and its operator edits survive regrouping, splits and evidence turnover. These rules went through **5 review rounds** and were checked against a randomized day-by-day simulation with retention turnover, long bridges and edits. That simulation is committed as the opt-in `TestCampaignWorldSimulation` (`internal/campaign/world_sim_test.go`, skipped unless `SHARDLURE_CAMPAIGN_SIM=<trials>` is set, so CI never runs it): run `SHARDLURE_CAMPAIGN_SIM=300 go test ./internal/campaign/ -run TestCampaignWorldSimulation -v` before and after changing any identity rule and compare the per-class failure counts it logs. The six **hard-invariant classes** (`simHardClasses`: shuffle, alias-cycle, fixpoint, merge-alias, removed-actor, id-change-same-evidence) **fail the test**, in the batch runner and the single-seed replay; the rest (home-collision, id-lost-*, organic-churn, ambiguous-edit) is expected residue, stays informational, and the header explains it. The hard classes used to be tallied beside the residue and never failed, so a regression that wrote an alias cycle or broke determinism passed whenever someone ran the sim. An unparsable `SHARDLURE_CAMPAIGN_SIM_BASE`/`_SEED` is fatal rather than silently seed 0. Load-bearing rules:
  - **Explicit merges persist through evidence turnover**; a merge is not undone when the evidence that happened to connect the two lineages ages out.
  - **Edits resolve through *merge* aliases only.** Automatic aliases from a transient bridge never redirect an edit: otherwise a merge naming an ID that was briefly absorbed fused an unrelated campaign forever.
  - The API records edit IDs **literally**; `Group` is the single interpreter of what an ID means now. Resolving in the request would bake in whatever the alias table said at that instant.
  - Ignore-evidence and remove-actor apply **before** union, so a removed actor can no longer bridge the campaign back together.
  - A merged campaign shows the **most recent rename** across its merged lineages (last rename wins).
  - **An edit that names no campaign is skipped** (rename/notes/remove_actor/merge with an empty ID, or a merge with an empty target), as `CampaignIdentity` skips an empty-ID assignment; `ignore_evidence` names a value, not a campaign, and stands. One such row used to emit a campaign whose ID is "", which `SaveGrouping` rejects whole (`ErrInvalidGrouping`), so campaigns never updated again.
  - **`Group(ctx, in)` is near-linear and cancellable.** Attribution used to enumerate, per floating value, every lineage each of its actors carries: O(n²) on attacker-shaped input (a bridge chain of m=4,000 took 18.5 s; now ~0.2 s). It now stops at the second distinct lineage (a bridge actor settles a value in O(1)), never walks the heaviest actor of a value, and memoises the tally per distinct actor set. **Honest caveat:** this is near-linear on every attacker-cheap shape, not O(n log n) for every input — "which lineage has the most distinct actors of this value" is a set-intersection count with no general near-linear exact algorithm, so two fat actors plus a distinct light actor per value still cost the second fat actor's set per value. The pre-fix functions are kept as `attributeReference` and `TestAttributionMatchesReference` requires identical output on 3,000 random worlds; `TestGroupScalesOnBridgeChain` bounds the chain (relaxed under `-race`). `Group` checks `ctx` between phases, components and attribution rounds and returns `ctx.Err()` with an empty `Output`; the worker passes its tick context, so a regroup cut by shutdown never reaches `SaveGrouping`.
  - **Known limitation (accepted):** a family whose first evidence arrives in a session shared with an existing campaign can inherit that campaign's ID and name after the bridge ends. Membership stays correct, and constant-evidence campaigns such as the Outlaw key are immune.
  - Suggested names come only from indicators an attacker cannot forge (the known Outlaw key fingerprint → "Outlaw/Dota", a payload the classifier names `redtail` → "RedTail"), shown until the operator confirms a name.
- **Persistence (`internal/store`).** `SaveGrouping` **replaces** `campaign_ids` with `Output.Assignments`; it does not upsert. `Group` was certified against replace semantics (the next run is fed exactly the previous assignments); under upsert, rows `Group` deliberately dropped came back as stale ownership claims and fused campaigns it had kept apart. Saves are **fenced by `lastEditID`** inside the same `writeMu` transaction: `ErrStaleGrouping` means "an edit arrived; regroup next tick" — it is not a failure and triggers no backoff. A grouping with any empty ID is rejected whole (`ErrInvalidGrouping`): an empty assignment fed back into the next run emits a campaign whose ID is "". A name matching several campaigns (several "Outlaw/Dota" components are normal) is `ErrAmbiguousCampaign` → HTTP 400 / CLI error, never a silent pick of the wrong one; the error is a `*AmbiguousCampaignError` carrying **every** matching ID from the same `lower()` query (no cap; the CLI once listed 1,000 and missed the oldest), which the API appends and `campaign show` prints (IDs are our own `c-<hex>`, never attacker text). Campaign detail lists (members, HASSHes, clients, hosts) are capped at `campaignDetailCap` (500) with true totals (`membersTotal`… in JSON), and both the dialog and `campaign show` disclose "showing N of M" (the CLI silently printed the first 500; it also prints the newest 5 edits as an `EDIT/WHEN/WHO/ARG` table through `termSafe`, noting "showing 5 of N edits; the dashboard has the full history"). `GetCampaign` reads everything in **one read-only transaction** (one WAL snapshot; `ensureArtifactsTable` runs before it opens): read piecewise, a `SaveGrouping` re-keying between the summary and the member reads returned a campaign with 0 members. `GetScript` does the same (one snapshot for the script row, its totals and its list): the session list is capped at `campaignDetailCap`, and `ScriptDetail.SessionsTotal`/`ActorsTotal` are true `COUNT(*)`/`COUNT(DISTINCT actor_id)` over the fingerprint (off `idx_session_scripts_fp`) — the dialog used to print the distinct actors among the newest 500 sessions as the script's actor count. **Every capped campaign/script surface says "showing N of M"**: the two list endpoints carry `total` (`CountCampaigns`/`CountScriptFamilies`, floored at the rows returned; a failed count omits it and logs through the rate-limited `listTotalErrLog`) against their default 200-row page; `/api/intel/script` sends `sessionsTotal`/`actorsTotal` from the store counts (not the family's materialised variant figure, which can go stale); and a family's variants are capped **largest-by-sessions first** by `capVariants` — `listVariantCap` 50 on the 30 s list poll, `scriptVariantCap` 200 in the on-demand dialog (plus the shown fingerprint and the representative) — beside a true `variantsTotal`. A family stores one variant per member fingerprint with no bound, and a bot whose scripts differ only in kept text mints one per session, so the list response had no bound at all. There is no load-more: the palette searches only the listed rows. Automatic membership never writes `actors.campaigns` (that column is operator annotation). Evidence, lines and settled scripts **follow event retention** (`purgeCampaignDerived`): it runs after the event chunks and **before** the orphan-actor sweep, so the bulk goes in bounded chunks and the sweep's single transaction only sees an orphan's sessions still inside retention (it deletes their lines through their `session_scripts` rows, which is what let the per-purge LEFT JOIN orphan-line scan go). Retention deletes **whole sessions** per transaction (up to ~5,000 lines, rows and lines together): deleting lines by rowid split a long session across chunks and a settle between chunks fingerprinted the surviving suffix. The price of that rule, accepted: events age out by event time and sessions by their `last_seen`, so a session straddling the cutoff keeps its lines for already-purged events until a later purge's cutoff passes its `last_seen` (the next one, for any session shorter than the purge interval), and a reset or replay inside that window re-records only its surviving suffix — bounded by one session's duration at the cutoff. A `purgeCampaignDerived` failure does not stop the purge — it is `errors.Join`ed into whatever the rest returns, so core event/actor retention keeps running and a later error cannot swallow it (a cancellation still returns at once); campaigns with an operator name or notes persist with no active members; merge-, remove- or ignore-only lineages disappear once their evidence ages out, as automatic ones do.
- **Operator edits (`POST /api/intel/campaign/edit`).** **`ignore_evidence` values must have the shape their kind's evidence carries** (`campaignIgnorableKinds`): `payload:` and `script:` take lowercase 64-hex (`^[0-9a-f]{64}$`, lowercase because evidence is stored lowercase), `ssh_key:` takes `^SHA256:[A-Za-z0-9+/]{43}$`, else 400. The edit log is append-only, so `payload:deadbeef`, uppercase hex or `sha256:` used to be recorded (and wake the worker) while matching nothing, forever. An **empty rename clears the name** (recorded literally as `rename ""`; `Group` reads the latest rename across merged lineages, so the suggested name shows again). A clear still counts as an edit, so it never changes which lineage owns the ID, and a lineage whose only edit is a clear fails the "name or notes" rule and is not kept. **`remove_actor` must name a current member** of the campaign or of a campaign merged into it, else 400 `actor X is not a member of campaign Y`: `campaignHoldsActor` expands the ID through **merge aliases only** (`campaign.MergeAliases`, the function `Group` uses) and `store.CampaignHasMember` matches that group literally, deliberately not following stored aliases — those include automatic bridge aliases, so an actor reachable only through a bridge got 200 although `Group` applies the removal to the lineage the edit names, where it does nothing. Refusals name the unknown ID and its role (`unknown campaign` vs `unknown merge target`). The UI's edit POST aborts after 15 s so a hung request cannot defer the dialog's reload forever.
- **Worker (`internal/campaign/worker.go`).** **One process runs the pipeline per database.** `shardlure live` and a separately started `shardlure web` both start the worker, and assign/prune, the version reset and the hold release assume a single sequential caller, so every tick first takes a **cross-process lease** (`store.AcquireCampaignLease`: one `ingest_state` row, `source='campaign'`/`path='worker-lease'`, `head_sig` = `<pid>:<random>` owner, `offset` = expiry; 60 s TTL, renewed once less than half remains — one small write per ~30 s — and again before the settle and regroup phases, so a tick can lose it only if one phase stalls over 30 s; the acquire is one conditional upsert plus read-back in one write transaction, so two processes racing an expired lease see one winner). **A non-holder reads before it writes**: the row is read on a plain connection first, and a lease held by another owner and unexpired returns `(false, nil)` with no write. The conditional upsert alone still took SQLite's write lock to learn "held elsewhere", so behind a long writer in the other process (a CLI `--replace` is one multi-minute transaction on prod) every non-holder tick waited `busy_timeout` and failed with `SQLITE_BUSY` — counted as a worker failure, with backoff and a logged error. The read is only an admission check, never the decision: a stale read that admits a contender still meets the conditional write. A process that does not hold it skips the tick quietly (`ErrLeaseHeldElsewhere` → nil to the monitor, no backoff, one log line naming the holder when that changes; `Regroup` returns the error) and, on regaining it, treats the acquire as a **takeover**. A takeover is an acquire while this process holds no lease **or its lease has lapsed on its own clock** (a phase stalled past the TTL, so another process may have held and released it unseen); it resets `versionChecked` (re-run the normaliser version check next tick: a `scripts --rebuild` may have deleted the version row meanwhile). Only a lease seen lost counted before, so a long-running `web` that took the lease back missed a requested rebuild until it restarted. **The rebuild hold is read from the store on every tick that could regroup** (`rebuildHeld` = `ScriptRebuildHold`, after the record phase and before the regroup decision; one primary-key read while no hold exists). It used to be cached once it read clear (`holdClear`) and re-read only after a restart or takeover, on the theory that only this process's own version reset could arm a hold — but a CLI `ingest cowrie --replace` arms one at any time, in another process, and a cached "clear" regrouped straight through it (as did a lapsed holder through another process's hold). A `(true, nil)` answer also covers "the hold restarted under me" (a replace committed mid-check) and is handled like any held tick. **The save is fenced inside its own transaction**: the worker calls `store.SaveGroupingAsLeaseHolder`, which checks `head_sig == owner AND offset > now` in the replace transaction and refuses with `ErrCampaignLeaseLost` (an empty owner is refused, never unfenced; the 5-argument `SaveGrouping` remains for fixtures). A renewal before the save is not a fence: a wall-clock step let another process take the lease over and release it inside one `Group`, and the stale save still landed. The same transaction also compares the **recorder reset epoch** with the one the tick read **before its hold check** (`EvidenceResetEpoch`) and refuses with `ErrStaleGrouping` (retried, no backoff) when it moved: a CLI `--replace` committing between the hold check and the regroup's evidence reads left the regroup looking at emptied evidence, and the save, which moved neither the lease nor the edit log, dropped every campaign's identity. The epoch must be read before the hold check, not merely before the reads — the replace bumps it and arms the hold in one transaction, so a read in between would match at save time. Mid-tick renewals use `store.RenewCampaignLease`, which never inserts or re-takes, and `renewLease` ends the tick with `ErrLeaseLapsed` when it finds the lease lost or lapsed (the regroup stays owed; the next tick retakes the lease as a takeover) — a mid-tick re-take used to happen after the tick had already checked the rebuild hold, so the tick regrouped through another process's hold. The lease is also renewed before `Group` (classification can open thousands of payloads on a cold memo), and prune checks the clock half; the cost is one small write per regroup. `Worker.Close` releases it so a restart hands over at once; a crashed owner is replaced when the lease expires. A standalone `web` against an offline-ingested database is simply the only worker and still builds campaigns; a Cowrie `--replace` leaves the lease row alone (it arms the rebuild hold instead, see above). One goroutine then runs (once per process: the `script.Version` check) → record → settle → assign → regroup/rebuild (`Group` + `SaveGrouping`, then `RebuildScriptFamilies`; skipped while a script rebuild holds) → prune (only on a tick that settled or regrouped, so an idle tick takes no `writeMu`), and assign/prune assume that single sequential caller. The **recorder** normalises **outside `writeMu`**: phase 1 reads the window with no lock and runs `EncodeLine`/`ExtractKeys` (attacker-shaped CPU, ~1 µs/byte), phase 2 is a short transaction that re-checks the cursor and the reset epoch (see the hold above) and writes by event id (IDs are `AUTOINCREMENT`, never reused). Phase 2, `SaveGrouping` and `SettleSessionScripts`' write phase write **multi-row statements** (`execBatched`, `batchParams` = 256 bound parameters each; the settle UPDATE is a `VALUES` CTE joined in `UPDATE … FROM … RETURNING`, keeping each session's `updated_at` guard and yielding the matched sessions for the scripts upsert — 2,000 sessions 121–138 ms → 60–64 ms of `writeMu` on x86, flat across 64–1,024 params, plan `SCAN v` then a primary-key `SEARCH`), not per-row or prepared statements: modernc.org/sqlite re-runs `sqlite3_prepare_v2` on every `Stmt.Exec`, so `tx.Prepare` saves only the Go side and the cost is the statement count. A dense window (5,000 short commands across 1,000 sessions) held `writeMu` 433–571 ms on x86 per-row, 330–370 ms prepared, **63–78 ms batched**; `SaveGrouping` of 10,000 assignments 158–191 → 100–115 ms. Larger batches do not help (binding is O(params²) in the driver). `SaveGrouping` also rejects a duplicate `(kind, value)`, campaign ID or member up front (`ErrInvalidGrouping`) instead of failing on a UNIQUE constraint mid-transaction. Normalising inside the transaction let ~128 hostile 64 KiB exec sessions hold `writeMu` 4.5 s on x86 (measured; 29–53 ms after the split) — never call `script.*` under the lock. It walks events past a durable cursor (`ingest_state` `source='campaign'`) in **5,000-rowid windows, one `writeMu` transaction each** (the `MaintenancePurge` convention; a 50,000 window held `writeMu` 0.4–1 s on ARM), also byte-capped, within a 5 s per-tick budget, releasing `writeMu` between windows so ingest interleaves with a long backfill. `evidenceScanQuery` writes `+source='cowrie' AND +kind IN (...)`: the unary `+` keeps those columns out of index selection, because commands are ~1% of events and answering `source='cowrie'` from `idx_events_session` scans most Cowrie rows under `writeMu` — the v2.8.0 HASSH-repair regression on ARM. A query-plan test pins it; don't drop the `+`. Regroups run every 10 min, once after a backlog drains (judged by how a tick *ends*: a burst larger than one window that drains inside the tick is ordinary ingest and owes no extra regroup), and on `Wake`: **edits wake the worker instead of regrouping inside the request** (`POST /api/intel/campaign/edit` records and returns; a request-side regroup raced the worker's own save). `Wake` is per process and only the lease holder regroups, so an edit POSTed to a `shardlure web` beside the `live` daemon would wake the wrong process: every unheld tick therefore also reads `store.LatestCampaignEditID` (one primary-key `MAX(id)`, no lock) and regroups when it exceeds `editsSeen`, the largest edit ID the last saved grouping read — an edit recorded by any process applies on the holder's next tick, not at its next scheduled regroup. **Nothing regroups while a tick ends with a backlog**: the regroup condition is `!held && drained && (woken || pending || schedule)`, and the wake flag and the `LatestCampaignEditID > editsSeen` check are read only on a drained tick, so a `Wake` during a backlog stays set (not consumed) and the drain's owed regroup applies the edit. A regroup over a partial backlog sees only the evidence recorded so far, and `SaveGrouping` replaces `campaign_ids` with that, so every campaign whose evidence was still queued came back under a fresh ID with its name on an empty shell (reached through `ingest cowrie --replace` plus a restart, or an edit during a first-start backfill). `editsSeen` starts at 0 after a restart, but that first drained tick owes a regroup anyway. `familyOf` opens payloads through pinned descriptors: `safefile.OpenRoot(cfg.CaptureEvidenceDir())` once per worker (a failed open is retried on the next lookup and **logged once per failure streak**, by `safefile.Category` only, never the path, with what the directory must satisfy, plus one line on recovery — a symlinked or unsupported root used to leave every payload unclassified and unlinked with nothing in the log; `Worker.Close` releases it after the workers are joined), a lexical mapping of the recorded path onto the root, then `Root.OpenRegular(rel)` and `bazaar.ClassifyFile(*os.File)` on that descriptor. The old `EvalSymlinks`-then-open had a check/use gap, and in-root symlinks and hardlinks were classified. A payload that yields no family never links, but **a policy refusal and a read failure are different answers** (`unclassified` vs `unreadable`). **Policy refusals fail closed all the way** — no link and the stored assignment is dropped: symlinks anywhere on the path (`ErrUnsafePath`), hardlinked files (`Nlink` > 1) and non-regular files (`ErrNotRegular`; a FIFO never blocks: `O_NONBLOCK`), paths outside the root. **Read failures** — permission or I/O errors and every other `OpenRegular` error, an evidence root that does not open (missing, symlinked or unsupported: deployment state the operator fixes), a DB error or no fetched row in the artifact lookup, no configured root, a cancelled context, a classifier read error (`ClassifyFile` returns read errors that `Classify(path)` still ignores) — also do not link, but `linkingOccurrences` lists the value once in **`Input.Unreadable`** and `Group` **carries its previous assignment** (unless it is ignored), the rule it already applies to a value only a removed actor carried; a carried assignment fed back in is a fixed point. Before, every failure dropped the assignment, so one failed read on a restarted process's first regroup (the memo is per process) minted a fresh ID for a renamed campaign once the file read again, its name stranded on an empty shell. Suspending regroups instead was rejected: one permanently unreadable file would freeze every regroup and edit on the deployment. The state is logged once per streak and once on recovery (`reportUnreadable`). Neither refusal is **memoised**, so both are retried every regroup (only successes are cached). A payload read but given **no family name does link**. Payloads are classified by bytes and never executed.

### Safe files, backup and recovery (`internal/safefile`, `internal/backup`)
`safefile` opens everything through pinned descriptors (openat2, falling back to openat under systemd seccomp), rejects symlinks/hardlinks/mount crossings and writable-by-others ancestors, and publishes with no-replace renames plus `fsync`. `backup create/verify/restore` builds on it: snapshots come from SQLite's online backup API, bundles are staged `.incomplete` and published only after every write/`fsync`; **a create that fails before publication removes its own staging directory** (`removeOwnStaging`, Linux only: the output parent is reopened `O_NOFOLLOW` and must match the pinned dev/ino, the name must have the `.shardlure-backup-*.incomplete` shape and the entry the created directory's dev/ino/uid, and the walk goes through directory descriptors, unlinking symlinks rather than following them and never crossing a filesystem), because a refused `--include-file` used to leave a staging directory holding a database snapshot beside the requested output. A published output from a late failure (after the rename, final sync) keeps its `.incomplete` marker and is reported as retained; a failed cleanup, or any non-Linux platform, keeps the staging directory and the CLI prints its path; a raced destination or another run's staging is never touched. Restore only ever targets a directory that does not exist, remaps evidence paths, resets Cowrie cursors for deduplicated replay and writes a capture/retention-disabled `shardlure.recovery.yaml` plus `recovery-report.json`. **Nothing here starts services or deletes old bundles** (the only deletion is that run's own unpublished staging). Evidence deletion during retention requires an explicitly configured evidence root: a path read from the DB alone never grants delete authority.
- **Refusals name the path and the reason.** A `safefile` output check that fails returns a `*safefile.PathRefusal` (it unwraps to the old sentinel, and its `Error()` still omits the path, keeping the package's no-supplied-paths-in-errors contract); `backup.RefusedPath` exposes path + reason and `explainRefusedPath` (`cmd/shardlure/backup.go`) prints both, plus the remedy, for `backup create`, `backup verify`/`restore --input` and `backup restore --to`. Before, prod got only `backup: filesystem or database operation failed` for `--output /srv/...`: every ancestor must be owned by root or the running user and not group/other-writable (unless sticky), and `/srv` was owned by `ubuntu` (uid 1000), which could swap directories mid-write. Use a root-owned directory such as `/var/backups`; the check is deliberate and was not relaxed. **The remedy follows the refused side and the failed check** (`refusalSides.side(path)`): a path inside `--output`/`--to` or an ancestor of `--output` is the output; inside `--input`, the bundle; an ancestor of (or equal to) an `--include-file`'s directory, the include; an ancestor of (or equal to) the config directory — also the fallback in `create`, covering the data, evidence and Cowrie roots — a config source. A shared ancestor goes to the side opened first (config, then output, then include — the real order in `backup.Create`; assuming includes opened before the output was the 2894c07 bug), and `ErrPermission` is always the output's, because ownership refusals come only from `Root.CheckOutput`. A source gets `refused source "<path>": …; point the config (-config or SHARDLURE_CONFIG) and the data, evidence and Cowrie paths it names at the real directory (no symlinks, …)` (an include: `point --include-file at a file in the real directory`), an output or bundle gets `choose an output directory / a bundle path …` worded per check (symlink, unsupported filesystem, changed, ownership). A symlinked config or evidence directory used to be told to choose another output directory. **A refused source *file* is named too**: `backup.refuseSourceFile` wraps a refused no-follow open of the config file or an `--include-file` (symbolic link, not a regular file, more than one hard link, unsupported filesystem, changed) in a `PathRefusal` carrying that file's path, includes are probed with `OpenRegular` during inventory exactly as the copy opens them, and `side()` maps the exact config file to the source side and an include file to the include side. A symlinked `--include-file` used to fail as `backup: filesystem or database operation failed` and a symlinked config as `invalid or missing configuration`, with no path; missing files and other errors are returned unchanged.
- **Rollback.** Schema migrates forward on first start, so rolling back means restoring the pre-upgrade bundle, not pointing an old binary at the migrated DB: a binary can snapshot only schemas up to its own `LatestSnapshotSchema`, so v2.8.0 (schema 24) and the campaigns rc1 (schema 25) cannot create backups of a v26 database. **Scripts are not re-encoded after a round trip.** An older campaigns build (rc1, implicit `script.Version` 1; any build stamped 2, 3 or 4, such as rc2) run on a current (`Version` 5) database records new lines in its own encoding but never touches the stored version row, so upgrading again sees a matching `5` and keeps those lines: the same script then fingerprints differently for sessions recorded under each build. To force the rebuild, run `shardlure scripts --rebuild` (as the service account: the DB is 0600) and **restart every `shardlure live` and `web` process using that database**, not only `shardlure-live`: the process that holds the worker lease is the one that must re-run the check, and a separately started `web` can hold it. It deletes only that version row (`store.ForceScriptRebuild`); a missing row is treated as a mismatch (`ResetScriptsForVersion`), and the check runs once per worker process (and again after a lease takeover), which is why the restart is required — a process that keeps holding the lease does not notice. The Version 4 and 5 resets also rebuild `ssh_key` evidence (see above). Campaign names and IDs survive through the same hold and carry as an upgrade.

### Health, lifecycle and origins (`internal/observability`, `cmd/shardlure/live_lifecycle.go`)
One `Monitor` per process holds fixed, mutex-protected worker/phase state; samplers refresh it every 5 s (1 s budget, readiness max age 15 s, expensive gauges once a minute). `/healthz`, `/readyz`, `/metrics` follow the `/debug/*` access rule and read only monitor snapshots. Startup is cancellable: the root signal context exists before config/store open, seeding waits for the listener, app APIs return 503 while starting/draining, and every worker is joined before the store closes. Reverse-proxy trust needs both `dashboard.public_origin` and `dashboard.trusted_proxies`; forwarded headers never grant trust.

## Web layer (`internal/web`)

- Assets are `go:embed`ed (`embed.go`): `index.html` + `intel.html` (two dashboards), `themes.css`, `cobe-globe.js`/`cobe-boot.js`, `vendor/vis-network.min.js`, `vendor/cobe.esm.js` (vendored globe engine — no CDN), the brand assets `logo.svg`/`logo-180.png`/`favicon.ico`, and **`fonts/`** (`fontsFS`: latin woff2 subsets of the six families the themes resolve + a generated `fonts.css`, served by `handleFont` under `/fonts/`). Every CSP fetch directive is `'self'` — fonts were the last third-party host; `scripts/fetch-fonts.sh` regenerates the directory with **content-hashed file names** (`inter-var-<sha8>.woff2`, so the route's `immutable` cache header is honest; the test checks name against bytes), and `TestFontsAreSelfHosted` pins that every quoted family in a theme stack is vendored, so adding a font to `themes.css` without re-running the script fails the build. HTML is served behind auth; static JS/CSS, fonts and the brand assets are unauthenticated — a favicon is requested before any token exists, and none of them carry telemetry. **vis-network is loaded on first use** (`ensureVis()` in the pivot-graph refresh), not from `<head>`: it is 689 KB for a third-tab panel.
- **Two dashboards:** `index.html` = the globe view (polls `/api/dashboard`); `intel.html` = the tabbed analyst console (Overview/Blue/Red/Settings, full `/api/intel/*` surface).
- **Auth is bimodal** around `SHARDLURE_DASH_TOKEN` (read live via the keystore, `crypto/subtle` compare): `/api/*` is **header-only** (`guard` → `Authorization: Bearer`). Read endpoints wrap that in `guardRead`, which additionally rejects anything but GET/HEAD **with an `Allow` header** — a 405 without one tells the caller nothing (`route_method_test.go` pins both the wrapper and that the bulk of `/api/*` uses it). Mutating endpoints (`*/upload`, `*/submit`, `*/report`, `/api/settings/save`…) take bare `guard` and check the method themselves. `/debug/*` uses `guardDebug`, which in token-less open mode additionally requires a loopback TCP peer (pprof never rides along with the open-dashboard convenience mode); the two *page* routes accept `?token=` in the query too (a browser nav can't set a header — the page then stashes the token and uses the header for all API calls; `fetch` is monkey-patched to inject it). Startup **refuses to bind** if the token is empty AND the listen addr is a public routable IP; otherwise open (designed for Tailscale/loopback).
- **Open mode refuses cross-site writes** (`origin_policy.go`). Without a token, nothing but the browser's own labels stops a page the operator visits from driving a mutating route, so `guard` (every mutating or quota-spending route, **every method**) calls `refuseCrossSiteBrowser`: a request with neither `Origin` nor `Sec-Fetch-Site` is a non-browser client (curl, CLI, scripts) and passes; `Sec-Fetch-Site: same-origin` passes **on its own** (a page cannot set it; also matching `Origin` against the Host the server sees broke every write behind `tailscale serve`/Caddy with no `dashboard.public_origin`, where the browser says `https://name` and the server sees `http://127.0.0.1:8080`); `Origin` equality with the dashboard origin applies **only when `Sec-Fetch-Site` is absent** (old engines). Anything else (`same-site`, `cross-site`, `none`, a `null` or foreign `Origin`) is 403. Token mode is unchanged: a bearer header cannot be forged cross-site. That check cannot see **quota-spending GETs**, because browsers send no `Sec-Fetch-*` to a plain-HTTP origin (the primary `http://<tailnet-ip>:8080` deployment) and a GET carries no `Origin`, so an `<img src=…/api/intel/payload/vt?sha=…>` on any page could spend VirusTotal quota. `requireQuotaHeader` therefore makes `/api/intel/payload/vt` and `/api/intel/enrich` demand `X-ShardLure-Request: 1` in open mode (a custom header needs a CORS preflight the server never answers); `intel.html`'s fetch wrapper is always installed and sets it on every `/api/` request (the Bearer token only when one exists), and curl users add the header themselves.
- **Open mode answers only known Hosts** (`host_policy.go`, `requireKnownHost`, which wraps the live handler in `RunContext`, so it covers every route). Without a token, the same-origin labels above are judged against the request's own Host, so a DNS-rebinding page at `evil.example:8080` is same-origin with itself and passes them all — and reads the whole API. The one thing it cannot change is the Host header its browser sends. Every token-less request's `Host` must therefore name this dashboard, or it gets **421 Misdirected Request**:
  - the **listen IP**, exactly (open mode already refuses wildcard and hostname binds; `--tailscale` makes it the tailnet IP, e.g. prod's `100.124.3.67`);
  - any **loopback** IP and `localhost` (for SSH tunnels);
  - the **`dashboard.public_origin` hostname**, exactly;
  - **MagicDNS**: the exact name `tailscale status --json` reports as `Self.DNSName` and its first label (`tailscaleSelfDNSName`, a `sync.OnceValue` run once at startup with a 2 s budget, so a wedged `tailscaled` never delays the dashboard; this covers a node renamed in the admin console). As a fallback, and always alongside it, names derived from `os.Hostname()`: the first label, `sanitise(first label)` and `sanitise(whole name)` (outside `[a-z0-9-]` → `-`, dashes trimmed, cut to 63 — Tailscale's own sanitising, so `my_box` is `my-box`), each with an optional `-<1..4 digits>` de-duplication suffix (a second `arm` is `arm-1`), alone or as `<label>.<one-label-tailnet>.ts.net`. Matching only the raw hostname answered 421 to exactly those Tailscale-derived names. The `ts.net` form is a pattern rather than an exact name because the tailnet label is not knowable offline without the CLI; `ts.net` names resolve only through a tailnet's own MagicDNS, so public DNS cannot answer for them.

  Matching ignores the port (a rebinding page must already use the dashboard's port; the name is what it cannot fake), is case-insensitive and drops a trailing dot. A request with an empty Host (HTTP/1.0) passes. Token mode does no Host check (a bearer header cannot be rebound, and a proxy may present any name). The token is read per request, so setting it lifts the check at once. **A node renamed away from its OS hostname with no working `tailscale` CLI, or one reached by a LAN DNS name, needs `dashboard.public_origin` or a token.**
- **Dashboard query caching lives here, not in `store`** — and it exists for a reason (comments document prior OOM/IO). `summaryStatsCached` is now a **combiner over three tiers keyed by how fast each value changes**: `liveSummaryStatsCached` (`statsTTL` 10s: event/actor counts, intent/playbook counts, 72h hourly-by-kind, Cowrie liveness), `distributionSummaryStatsCached` (`distributionStatsTTL` 1m: kind/source distributions) and `lifetimeSummaryStatsCached` (`lifetimeStatsTTL` 5m: unique IPs, countries, top IPs/users/commands, all-time session count — the unbounded all-history scans that were the remaining ~2.7s behind every `statsTTL` expiry on prod). `countriesCached` rides `lifetimeStatsTTL` too. `TestSummaryCacheTTLsAreTiered` pins the ordering; don't collapse a lifetime value back into the 10s tier. **Two rules inside the tiers:** a degenerate lifetime value (empty country list, zero countries while geo is enabled, a failed session count) is stamped with `lifetimeStamp(false)` so it expires on `statsTTL` — the geo table is filled asynchronously by the very handler that reads it, and caching the cold first read for 5 min froze the intel Attack Geography panel; and the combiner **serves a tier's last-good value when its refresh fails** (only a tier that has never succeeded is fatal), the same policy as `hasshCoverageCached`/`topCountriesCached`. `dashExtraCachedValues` (10s TTL) memoizes the two remaining full-window scans `/api/dashboard` used to run uncached (`HourlyEventCounts(72)` + `RecentShellSessions`); `eventsForWindowCached` (15s TTL, per-window, single-flight, **LRU-bounded to `maxEventsCacheEntries`=4 entries** so an authenticated client asking for many distinct exact windows cannot pin unbounded RAM; expired entries are evicted before live ones, last-good is served on a transient store error) memoizes the *bounded* windowed event slice shared by mitre/ttp/deobf/graph/wordlist/ioc — it returns `(events, total, err)`, and every intel handler calls `discloseWindowTruncation(w, len(events), total)` to set an advisory `X-ShardLure-Window-Truncated: returned/total` header when the cap bit. Don't remove these without understanding the poll-storm they prevent (N widgets × full scan every 5s).
- **Poll-path caches are stale-while-revalidate** (`swr_cache.go`, `swrCache[T]`): the three summary tiers, `dashExtraCachedValues` and `recentCountsCached`. Once a value exists, an expired read returns it at once and starts **at most one** background refresh, admitted through the server's `handlerDrain` (`s.bg.enter()`) and **run on the drain's context, which `bg.stop()` cancels** — so a shutdown interrupts an in-flight scan (the tier reads use `*Context` store variants; modernc turns a done context into `sqlite3_interrupt`) instead of `RunContext` waiting seconds for it against a store about to close, and a refresh cancelled that way is dropped like a failed one, never published over good data; a failed refresh keeps the last-good value and stamp, so the next read retries. Before, whichever request landed on an expiry ran the scans while every other poller queued on the mutex (on ARM, polled every 10 s, the summary tiers and `RecentShellSessions` cost 3.6 s and 3.5 s of a 60 s CPU profile); an expired `/api/dashboard` on a 640k-event DB went from ~2 s to 3–17 ms. Deliberately unlike `hasshCoverageCached`, the **first** value is computed synchronously under the mutex (a cold request gets data; `WarmCaches` fills them before ready), and `compute` returns the stamp so the lifetime tier keeps `lifetimeStamp`'s degenerate-value rule. `eventsForWindowCached` is **not** SWR: background refreshes of up to 4 LRU windows of up to 200k rows would churn memory for no measured gain. The **Brute-Force Radar** is derived from the cached per-actor counts (`store.TopActorRatesFromCounts`: sort in memory, 8 primary-key reads) instead of recounting the window on every `/api/intel`. `TopActorRatesFromCounts` skips only `sql.ErrNoRows` (an actor gone since the counts) and **returns every other store error** — it used to skip them all, so a closed or failing store rendered an empty radar with no error. The handler drops only the radar on an error (the rest of `/api/intel` is still 200) and logs it through `logOperationError` as the fixed category `web: intel_radar: operation_failed`, never the raw error, **rate-limited** by `opLogLimiter` to one line per 5 min (`radarErrLogEvery`) so a 5 s poll cannot flood the journal (the actor table's "Last cmd" read does the same through its own `lastCmdErrLog`, category `intel_last_command`: the column stays blank and the page renders, but the error is logged — `LastCommandsForActors` names its indexes with `INDEXED BY`, so a dropped index failed it on every poll until the next `Open`, and the blank column used to be the only sign); those counts are one `GROUP BY actor_id` over the two exact-time branches (`RecentEventCountsByActor`, with `actor_id<>''` kept outside the branches so it cannot pull in `idx_events_actor_ts`) instead of decoding every window event into Go. `RecentShellSessions` (and any session list with a command floor, `minCommands > 0`) takes candidate sessions from command rows only and aggregates each through `idx_events_session`, rather than grouping every session in the window. The `/api/intel` command reads use the v26 partial indexes (`LastCommandsForActors`: two per-actor `LIMIT 1` reads, never the global legacy index; `RecentCommands`: newest-first from `idx_events_cmd_ts`). Together these took `/api/intel` from **~766 ms to 11 ms of CPU per request** on a 640k-event backfilled DB; with 5% legacy rows it stays ~70 ms until the backfill drains the legacy index the `RecentCommands` legacy branch walks.
- **`hasshCoverageCached` is the one aggregate with its own, much longer TTL (5 min).** `store.HASSHCoverage` is a COUNT + SUM over every cowrie event ever ingested with no `ts` restriction, so its cost grows without bound as the DB does: measured at **1.28s on prod's 1.06M rows, ~10× the next-largest dashboard query** (`TopCountriesByHits`, 0.13s), and the biggest single contributor to a 4.6s `/api/dashboard` on each cache expiry against 4ms warm. With a 5s poll and a 10s `statsTTL`, roughly every second poll paid it. The figure is a *lifetime ratio* that moves fractions of a percent per hour, so minutes of staleness are invisible. Don't fold it back into `statsTTL`, and don't "fix" it with an index on `(source, hassh)` — v9 dropped a write-amplifying index for a reason and every event insert would pay for it.
- **Frontend accessibility + responsive contracts are pinned by `frontend_a11y_test.go`** (from the 2026-09-07 frontend UI audit, every finding reproduced in a real browser before it was fixed): collapsible panels are `<h2><button class="panel-toggle" aria-expanded aria-controls>` (a collapsed body is `visibility:hidden`, not just `max-height:0`, or its buttons stay tabbable); no `outline:none` anywhere — `themes.css` owns one `:focus-visible` ring per theme via `--focus-ring`; every static control has an accessible name and the generated Settings rows use `aria-labelledby` → `labelId(key)`; the search input is a `role=combobox` whose `aria-activedescendant` follows the palette selection; the two modals are native `<dialog>` opened with `showModal()` (focus trap, Esc, inert page, focus restore come from the browser); **every intel poller goes through `pollEvery`** (skips ticks while `document.hidden`; on return each runs only if more than half its period has elapsed, so a rapid hide/show cannot fire overlapping bursts) and `intel.html` may contain exactly one bare `setInterval(` — the one inside it; `index.html`'s single poller carries the same `document.hidden` guard and a last-run check; the download controls are `<button>`s, not href-less anchors; no inline `grid-template-columns` (an inline style beats every media query — `.stats.cols-5`); both pages have a ≤760px layout (intel: sidebar becomes a top strip, tables get a min-width and scroll in their panel; index: rails go static and the page scrolls, the live feed is *not* hidden, the globe's phone rules live in `themes.css` beside its desktop ones because that file loads last); `--dim`/`--dim-2` clear 4.5:1 against bg *and* every panel surface per theme (`TestDimTokensMeetContrast` computes it) and nothing is set below 10px; side-stripe `border-left` accents are banned. Legacy-palette `rgba(200,152,40,…)`-style tints were tokenised to `color-mix(in srgb, var(--token) N%, transparent)`, picking the token from the rule's own text colour.
- **The campaign/script dialog JS is tested by behaviour, under node** (`campaign_node_harness_test.go`): the harness runs `intel.html`'s real campaign block with the page's own `esc`/`fmt`, a recording `fetch`, abortable POSTs, manual timers and a native-like `<dialog>` close, and the tests drive the edit timeout, merge-target carry, clear-name, the hold park/keep/release, Esc cleanup (also mid-flight), the "showing N of M" cap notes, row buttons and the variant dialog. They replaced text pins, which failed on a pure reformat (a merge line split into a block) while a real mutation could pass; each behaviour test was checked to fail on its mutation. Only what node cannot see stays a text test: the markup, the 760 px CSS and cell classes, the single `setInterval`, and the palette (outside the block). **Without node the tests skip loudly; with `CI` set they fail** (`requireNode`), so CI can never pass with them silently not run — `ci.yml` has no `setup-node` step and relies on the `ubuntu-latest` image shipping node; if that ever changes the job fails rather than skipping. Number formatting assumes node's default ICU gives `1,234` (en-US and C locales). **Campaigns and scripts load once per page**: their block ends with an unconditional first load (the palette searches them on every tab), so the `#tab=red` deep-link line no longer calls `refreshCampaigns`/`refreshScripts` — it fetched both lists twice (`TestCampaignListsLoadOncePerPage`).
- **Density toggle** — comfortable (14px/12px) is the default; compact restores the original 13px. Unlike the theme it is **`localStorage` only** (`shardlure_density`, applied by an inline pre-paint script so there's no flash) — it is a per-screen viewing preference, not a deployment setting, so it deliberately has no keystore key.
- **Themes: 3 implemented** — `signal` (default; supports `data-mode="dark|light"`), `meridian`, `sprite`. `themes.css` defines exactly those and `validateSetting` hard-rejects anything else. Persisted as keystore `ui.theme` (+ `ui.mode` for Signal), server > localStorage, synced across tabs via `BroadcastChannel`. **One globe engine (Cobe)** for all themes — globe.gl and the Dragon theme were removed in v2.0.0.

## Performance

The README's four perf claims (incremental ingest, batched writes, dashboard query caching, actors indexes) are all **real and correctly implemented**.

**Fixed 2026-07 (a further perf pass — do not re-introduce the old behavior):**
- **Bounded windowed reads.** `EventsSinceAll` used to be `SELECT … WHERE ts >= ?` with no LIMIT, and `eventsForWindowCached` pinned the whole slice in RAM — a 30d wordlist poll on a multi-million-row DB was a full scan + hundreds-of-MB allocation. Now `EventsSinceCapped` bounds the fetch (`defaultWindowEventCap`) while reporting the true total, and handlers disclose truncation via the `X-ShardLure-Window-Truncated` header. Don't route a poll path back through uncapped `EventsSinceAll`.
- **The 5s landing path is fully cached.** `HourlyEventCounts(72)` and `RecentShellSessions` no longer run uncached on every `/api/dashboard` poll — they're behind `dashExtraCachedValues` (see Web layer).
- **Planner stats + pool tuning.** `PRAGMA optimize` runs at `Open` and each purge; `SetMaxIdleConns(8)` + `ConnMaxLifetime(1h)` stop pool churn.
- **Batched side-channel writes.** Per-tick session bindings (hassh/duration/arch/tty) commit in one `RecordSessionBindings` transaction instead of N separate `writeMu` acquisitions ahead of the event insert.

**Fixed 2026-09 (cache tiers + frontend):** the summary-stats cache was split into 10s/1m/5m tiers (see Web layer) so the 5s landing poll no longer drags the all-history aggregates along on every `statsTTL` expiry; the windowed-events cache got a hard entry bound; and the two dashboards stopped polling from hidden tabs, loading vis-network eagerly and fetching typography from Google on every page load.

**Fixed 2026-09 (fix-all round):** stale-while-revalidate poll caches, the radar from cached counts, the `GROUP BY` rate count, the command-only shell-session plan and the v26 command indexes (see Web layer). Don't route `/api/intel` back through a whole-history `ROW_NUMBER` or an uncached rate count.

**Known remaining (LOW, intentional):** `HourlyEventCounts`/`…ByKind` group on `substr(ts,1,13)` and `DistinctGeoCountryCount` does `COUNT(DISTINCT json_extract(...))` — neither can use an index for the *aggregation*, but the `ts >= ?` restriction is index-served and both are now well-cached, so leaving them avoids risking the working plan. Don't "optimize" these into a form that drops the `ts` index restriction.

## Conventions observed in this codebase

- Unknown CLI flags are **fatal, not ignored** (a typo like `--repalce` silently appending was a real bug — see `cmdIngest`). Match that: validate flags, don't swallow.
- **Config resolution has a system fallback, and it is not cosmetic.** `config.Load("")` prefers the invoking user's `~/.local/share/shardlure/shardlure.yaml`, then falls back to `/etc/shardlure/shardlure.yaml` or `/var/lib/shardlure/shardlure.yaml` (`resolveConfigPath`). The systemd unit passes `SHARDLURE_CONFIG`, but an operator shell does not: without the fallback `sudo shardlure share bazaar` opened an empty database in root's home *beside* the real 1M-event one and reported "no candidates" — indistinguishable from a broken feature, on every manual outbound run (there are no timers; all sharing is manual). A user who has their own config always keeps it, an explicit `-config` always wins, and an unreadable system candidate is skipped rather than fatal so a non-root CLI still works.
- **`--limit`: `0` means all/unbounded wherever it is accepted, and range checks are explicit.** The outbound commands (`share bazaar|urlhaus|threatfox`, `report abuseipdb`) bound *submissions after `Vet`*, not candidates; `0` is unbounded and a negative is fatal (`validateOutboundLimit`, one `error:` line, exit 1, checked before any key, store read or network step) — the intel packages still read any non-positive budget as no cap, so a typo'd `-1` used to make a run of irreversible submissions unbounded. `actors --limit` (default 25) accepts `0` = every actor or `1..1000` (`validateListLimit`) and refuses negatives and stray arguments — a negative used to reach `ListActors` and silently list everything. `campaigns`/`scripts --limit` (default 50) accept only `1..1000`; `0` is refused there, not "all", because their store lists cap at 1000. The `actors` 1000 bound is **not** that reason (`ListActors` has no cap and would honour 1500): it is a deliberate, uniform narrowing, and above 1000 the error points at `0` rather than quietly returning a shorter list. The usage text states each range (`actors [--limit=25] (1..1000, 0 = all)`, `campaigns|scripts [--limit=50] (1..1000)`). The three list commands parse through `parseCmdFlags`/`cmdExitStatus`: `--help` exits 0, a flag error exits 2 and is printed once (by the flag package, with the usage), a value error such as `--limit=-1` prints one `error:` line and exits 1 — `scripts` and `actors` used to print a bad flag twice and exit 1. Match this when adding a list command: document what `0` does in the flag help and refuse what you do not handle.
- Comments here explain *why*, often citing the bug a line prevents. When changing such code, preserve or update the rationale — several guards look removable but aren't (the dedup `source`-in-Go filter, the offset-by-consumed-bytes, the `writeMu`-not-1-conn choice).
- **New CLI output of attacker-derived data must go through `termSafe`** (`jsonTermSafe` for JSON, applied after marshalling). A command, filename, key comment or campaign name printed raw can carry terminal escape sequences into the operator's shell.
- Interfaces decouple `intel/*` from `store` (`UploadRecorder`, `ReportRecorder`, `KeyLookup`) — keep intel packages free of a direct `store` import.
- Secrets are never logged or returned raw; the settings API masks them (`maskSecret`) and reports only a db/env/unset source badge.
