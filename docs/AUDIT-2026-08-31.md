## 3) ELF family classifier — works, but yields no family on this corpus

`c818bf8`'s classifier is wired in and its file-kind, architecture and packing
detection all fire. Family attribution resolves on **shell scripts**
(`Traffmonetizer`, `Coinminer`/c3pool, `redtail`, `komari`) and the tags shipped
to MalwareBazaar carry arch + packing:

```
['elf','aarch64','static','packed','upx','linux']   x5
['elf','mips','static','packed','upx','linux']      x1
['bash','script','miner','redtail','dropper','linux']
```

But **no ELF in the current live corpus resolves to a family**. Two causes, both
by design: UPX packing compresses the Tier-A anchors, and the large samples
(19 MB, 26 MB) are Go-built proxyware the anchors don't cover. This is the
precision-first tradeoff working as specified — worth knowing, not a defect.

## 4) Defects and gaps

### D1 — CLI silently opens the wrong database (highest-impact finding)

`shardlure` resolves its config from `userDataDir()` (`~/.local/share/shardlure`)
unless `SHARDLURE_CONFIG` is set. The systemd unit sets it; **an operator shell
does not**:

```
sudo shardlure status                  ->  events: 5440      actors: 73
sudo env SHARDLURE_CONFIG=... status   ->  events: 1061098   actors: 6715
```

Three stray databases exist on the box (`/root`, `/home/het`, `/home/ubuntu`),
and `/root/.local/share/shardlure/shardlure.db` was written *by this audit's own
dry-runs* — they migrated and queried a 5,440-event decoy.

Consequence: every hand-run `share bazaar` / `report abuseipdb` / `reclassify`
targets an almost-empty DB and reports "no candidates", which is
indistinguishable from a broken feature. This cost real time during this audit:
the first `share threatfox --dry-run` returned "no candidates" while the live DB
held a valid one.

There are no systemd timers or cron entries for these commands, so **every**
outbound run on this deployment is a manual invocation — i.e. every one of them
is exposed to this trap.

Fix options: default the config path to `/etc/shardlure/shardlure.yaml` when it
exists; or have the CLI warn when a system DB exists at `/var/lib/shardlure` but
a user-dir DB was opened; or ship a shell profile export.

### D2 — `/api/dashboard` costs 4.6 s on every cache expiry

Reproducible, warm process, three trials:

```
cold (after 11s idle): 4.591s / 4.573s / 4.577s
warm (immediately after): 0.0038s / 0.0039s / 0.0082s
```

`statsTTL` is 10 s and the landing page polls every 5 s, so roughly every second
poll pays the full refresh. Timed individually under `sqlite3` (C build) on the
live DB:

```
HASSHCoverage      1.28 s   <- COUNT(*) + SUM(CASE...) over 1.03M cowrie rows, no ts bound
CountSessions      0.17 s   <- COUNT(DISTINCT session_id), no ts bound
TopSourceIPs(25)   0.12 s
HourlyByKind(72)   0.11 s
CountsByKind       0.10 s
TopCommands/Users  0.07/0.08 s
UniqueIPCount      0.01 s
```

~2.0 s in C; the endpoint measures 4.6 s end-to-end, the remainder being
`modernc.org/sqlite` (pure-Go) overhead on scan-heavy queries. These are
all-time aggregates with no time restriction, so the cost grows linearly with
the events table forever — it was tolerable at 846k rows and is not at 1.06M.

`HASSHCoverage` alone is ~64% of the SQL time. It is a lifetime ratio that moves
negligibly minute to minute; the cheapest correct fixes are a much longer TTL for
that one figure, or maintaining it as a counter updated at ingest.

### D3 — `reclassify` silently drops actors it cannot rebuild

```
reclassify cowrie (dry-run): 4 changed, 4922 unchanged, 0 without state of 5029 actors
```

4 + 4922 + 0 = 4926. **103 actors are unaccounted for and no counter or message
mentions them.** In `cmdReclassify`, legacy rows go to `legacyIDs` (no counter),
and the second loop does `if agg == nil { continue }` — also no counter.

The arithmetic confirms the cause exactly:

```
cowrie actors, flags=0, event_count>0, NO surviving events : 103
cowrie actors, flags=0, event_count>0, WITH events         :  24
4902 non-legacy + 24 rebuildable = 4926 accounted
```

Fix: count them and print, e.g. `103 unrebuildable (events purged)`.

### D4 — Retention purge leaves orphan actor rows

The 103 above are actors whose events were deleted by `MaintenancePurge` while
the actor row survived with a stale `event_count` and a frozen playbook:

```
cowrie:45.79.207.181 | unknown | event_count=4 | last_seen 2026-04-29
oldest surviving event: 2026-06-23
```

102 of the 103 carry `playbook='unknown'` — they *are* the entire residual
unknown population from §1. They can never be reclassified (no data), they
inflate the actor count on the dashboard, and their `event_count` is a lie.
Decide deliberately: purge orphans alongside their events, or mark them so the UI
and `reclassify` can exclude them.

### D5 — Two shipped commands are missing from the top-level usage text

`shardlure` with no args lists `share bazaar` and `share urlhaus` but not
`share threatfox`, and omits `reclassify` entirely. Both are fully implemented,
tested and wired to dashboard panels; they are simply undiscoverable from the
binary's own help.

### D6 — `CLAUDE.md` has drifted from the code

- It states the migration ladder is **v1→v17**; the ladder ends at **v18**
  (`sqlite.go:647`). The file's own comment warns "bump the v1→v17 figure above,
  which has silently drifted twice" — this is the third drift.
- It documents none of: the `reclassify` command, the `flags` column / v18 fold,
  the `handshake_scan` and `scanner_tool` playbooks, `intel/bazaar/elf_family.go`,
  or the density toggle.

Given how much this project leans on `CLAUDE.md` as the single source of
guidance, this is worth closing now rather than at the next drift.

### D7 — URL extraction keeps a trailing `)`

`internal/capture/urls.go:15` — `https?://[^\s"'<>]+` does not strip trailing
punctuation, so a command like `$(wget https://host/sh)` yields the URL with the
paren attached. Live evidence, both rows present:

```
https://217.60.195.113/sh    failed
https://217.60.195.113/sh)   failed
```

Effect is small but real: a duplicate junk artifact row per occurrence, a wasted
fetch attempt, and a polluted candidate pool. Strip trailing `)` `]` `}` `.` `,`
`;` when unbalanced.

## 5) Deployment posture (not code defects)

- **Dashboard is unauthenticated.** No `SHARDLURE_DASH_TOKEN` is set, so
  `/api/dashboard` returns 200 with no header, and `--tailscale` binds `*:8080`
  (intentional — `server.go:878` exempts wildcard binds in tailscale mode).
  **Currently not reachable**: verified from this machine over both the tailnet
  (`100.124.3.67:8080`) and wireguard (`10.229.33.1:8080`) — ufw's default-deny
  blocks 8080, which is not in the allow list. The exposure is one `ufw allow`
  away from being real, and credential/wordlist exports are behind that port.
  Setting a token costs nothing and removes the dependency on a firewall rule.

- **Zero observability.** `journalctl -u shardlure-live.service` has **no entries
  at all**, including for the service's own start on 2026-08-29. journald itself
  is healthy (cowrie logs fine, 210 MB of journals) — the retention is being
  consumed by an unrelated crash loop: `hermes-dashboard.service` has a restart
  counter of **72,224** and wrote **82,291** journal lines in 24 hours. Any
  ShardLure error, and its startup unauthenticated-dashboard warning, is
  unrecoverable. Fix the hermes unit or give ShardLure its own log retention.

- **Disk.** `/` is at 65% (29 G / 45 G). `/var/lib/shardlure` holds ~1.9 GB of
  `.bak` database copies from July/August migrations, plus the 1.0 GB live DB and
  a 130 MB mmdb. The pre-fold and pre-reclassify backups (803 MB each) have
  served their purpose.

- **`govulncheck` cannot run locally** — the installed binary was built with
  go1.26 and refuses a go1.27 module. Reinstall before claiming the go1.27
  vulnerability fixes are verified.

## 6) Resolution — all seven fixed (2026-08-31)

Every fix was written test-first and each test was mutation-verified (reverted the
fix, watched the test fail, restored it). Full suite green, `go vet` clean,
`-race` clean on all five changed packages, `ci-web-smoke.sh` passes.

| # | Fix | Where | Verification |
|---|---|---|---|
| D1 | `config.Load("")` falls back to `/etc/shardlure` then `/var/lib/shardlure` when the invoking user has no config | `internal/config/config.go` (`resolveConfigPath`) | **Proven on arm**: old binary `status` = 5,440 events, new binary = 1,061,559 |
| D2 | `HASSHCoverage` moved to its own 5-minute memo, off the 10 s `statsTTL` | `internal/web/server.go` (`hasshCoverageCached`) | 3 tests incl. TTL-ordering guard; race-clean |
| D3 | `planReclassify` extracted; adds an `Unrebuildable` counter so totals add up | `cmd/shardlure/main.go` | counters now sum to Total; mutation-verified |
| D4 | `MaintenancePurge` sweeps orphan actors + their `actor_ips`/`actor_users` | `internal/store/sqlite.go` | **103 orphans on arm, 0 with events, none newer than 124 d; 0 `unknown` actors remain** |
| D5 | `reclassify` and `share threatfox` added to usage | `cmd/shardlure/main.go` | test asserts every dispatched command is documented |
| D6 | ladder corrected to v18; new features documented | `CLAUDE.md` | claims re-verified against code, not the commit messages |
| D7 | balance-aware trailing-punctuation trim on extracted URLs | `internal/capture/urls.go` | 6 tests incl. IPv6 and balanced-paren guards |

**One fix was wrong on the first attempt, and live data caught it.** D4's orphan
sweep originally protected any actor with `campaigns` *or* `notes` set, reading
both as operator annotation. Checking the predicate against the production
database before trusting it showed it would delete **0** rows: `notes` is
machine-generated (`actor/builder.go` rewrites it as `"2 events, 0 usernames"` on
every rebuild), so all 6,716 actors carried one. The guard is now `campaigns`
only — the field whose model comment actually says "operator-assigned … reserved
for manual annotation" — and the sweep correctly identifies exactly the 103
orphans this audit found. Re-running the same query post-fix leaves **zero**
actors with an `unknown` playbook, closing §1's residual 1.5% entirely.

Two claims from §4 were also corrected while fixing:

- **D2's magnitude was over-attributed.** `HASSHCoverage` is 1.28 s of ~2.2 s of
  measured SQL, and ~10× the next-largest dashboard query (`TopCountriesByHits`,
  0.13 s; hourly counts, 0.05 s) — so it is unambiguously the right target. But a
  local 400k-row benchmark cut a refresh only 1.33 s → 1.05 s, because synthetic
  data weights the other aggregates differently. The end-to-end gain on the 4.6 s
  production figure is **not yet measured** and needs a post-deploy reading.
- **D7's blast radius is small**: the trim also drops `.` `,` `:` `!` `?` and
  unbalanced `]` `}`, and rejects anything reduced to a bare scheme.

### Deployed to `arm` — 2026-08-31 14:13 IST

Built on the box from tar-pushed sources (never `scp` — see CLAUDE.md), go1.27.0
linux/arm64 auto-resolved via `GOTOOLCHAIN`, `go.mod`/`go.sum` sha256-matched
against local, and the five changed packages' tests run **on arm64** before
install. Installed as `v2.5.0-auditfixes`; previous binary kept at
`/usr/local/bin/shardlure.bak-preauditfixes`, live DB backed up to
`shardlure.db.bak-pre-auditfixes-20260831-141058` (1.0 GB, via `sqlite3 .backup`,
safe on a live WAL database).

Post-deploy measurements:

| Fix | Before | After |
|---|---|---|
| D2 `/api/dashboard` recurring refresh | 4.69 s **every 10 s** | **2.68 s**, with the 4.67 s cost now paid once per 5 min |
| D4 actors / `unknown` playbook | 6,717 / 102 | **6,615 / 0** |
| D1 `sudo shardlure status` | 5,440 events | **1,061,709 events** |
| D3 reclassify summary | 4 + 4922 + 0 vs 5029 (103 missing) | `4 changed, 4924 unchanged, 0 without state, 0 unrebuildable of 4928` — **sums exactly** |
| Steady-state CPU (120 s sample) | — | 0.55% of one core; RSS 59 MB (was 108 MB) |

Both dashboards and every probed endpoint return 200, ingest is advancing, and
`journalctl -p err` is empty since restart.

Two things the deploy settled that the audit could not:

- **§5's "zero observability" was retention loss, not a logging defect.** The
  restarted daemon logs normally — including the unauthenticated-dashboard
  warning. The earlier entries had simply been rotated out of journald by the
  `hermes-dashboard` crash loop. That unit is still spamming and should still be
  fixed, but ShardLure logs fine.
- **D2 is a real but partial win.** 2.0 s came off each refresh, exactly the
  `HASSHCoverage` share. The remaining **2.68 s** is spread across the other
  unbounded all-time aggregates (`CountSessions`, `TopCountriesByHits`,
  `TopSourceIPs`/`TopUsernames`/`TopCommands`, `CountsByKind`) — none individually
  large, all growing with the events table. Closing that gap needs the same
  treatment applied to the group, and is not done.

One pre-existing defect surfaced and was **not** introduced by this work: three
`actor_ips` rows point at actor IDs absent from `actors`. Verified against the
pre-deploy backup — the same three rows and the same missing IDs were already
there, an artifact of cowrie actors being re-keyed from `cowrie:<ip>` to
`cowrie:<hassh>` when a fingerprint first appears. Small, harmless, unfixed.

The §5 posture items are unchanged and remain operator decisions: no dashboard
token, the `hermes-dashboard` crash loop eating journald retention, 1.9 GB of
stale `.bak` databases, and a stale local `govulncheck`.

## 7) Verdict

**All features audited are correctly integrated and working.** Nothing is
half-wired, no panel reads from a stale source, no gate is bypassable, and the
two headline fixes of this release (the v18 aggregate fold and the classification
pass) are confirmed on live production data with an 11× CPU reduction and a
74% → 1.5% drop in unclassified actors.

The seven findings above are one operational trap (D1), one growth-driven perf
regression (D2), two small correctness/reporting gaps around purged actors
(D3/D4), and three hygiene items (D5–D7). None of them break a feature.

Suggested order: **D1** (silently wrong data on every manual CLI run), **D2**
(user-visible and worsening), **D6** (cheap, and the file is load-bearing for
future work), then D3/D4/D5/D7.
