# ShardLure — Full Analysis & Audit (2026-08-21)

Scope: full codebase + live `arm` VPS (`ssh arm` / `arm:8080`, batch read-only ops), plus
web/GitHub comparison against comparable honeypot classify/capture projects.

---

## 1) What ShardLure is (verified from code)

ShardLure is an **SSH-honeypot attacker-identity engine**: it ingests OpenSSH journal
telemetry and Cowrie JSON, clusters attackers by **HASSH fingerprint** (Cowrie) or **IP**
(journal) rather than raw IP, classifies **playbook + intent**, captures payloads, maps
to MITRE ATT&CK, and serves a WebGL-globe dashboard + forensic TUI.

The whole app is a single Go binary; it's the culmination of 251 commits (~26k LOC Go,
~908 test functions, 215 test files). Deployment: real SSH moved to `2222`, Cowrie on
`22`, ShardLure `live` daemon tails Cowrie + journald into SQLite.

Key files read & cited:
- `CLAUDE.md` (the single source of guidance; `AGENTS.md` deliberately points to it)
- `PRODUCT.md` (positioning: "Identity over IP")
- `cmd/shardlure/main.go` (CLI/live daemon)
- `internal/actor/{playbook,builder}.go` (playbook + probe scoring, clusters)
- `internal/ingest/{cowrie,journal}/*` (ingest, dedup, incremental actor agg)
- `internal/capture/{fetch,urls,worker,runner}.go` (payload capture + retry)
- `internal/intel/{bazaar,urlhaus,threatfox,abuseipdb}` (outbound, w/ Vet gate)
- `internal/intel/{mitre,payload,ttp,deobf,ioc,wordlist,enrich,vt}` (intel)
- `internal/web/*` (dashboard, geo, auth)

## 2) Live deployment (`arm` VPS) — what I found

- **Box**: `aarch64` Ubuntu, kernel 6.17, up 13d 22h (healthy). Runs `shardlure live
  127.0.0.1:8080 --tailscale --cowrie=...` as `root`, unit `shardlure-live.service`.
- **Scale**: 846k events (825k cowrie, 21.6k journal); DB 766MB.
- **Actors**: 5,537 total. **Classification skew is real (see §5)**: 74%
  `unknown` playbook; intent almost entirely `probe` (4,145) / `unknown` (1,374);
  only 17 `deploy` + 1 `mixed`. Payloads: 375 cowrie downloads, 499 cowrie-sourced
  file-downloads, 24 fetched threats, 427 tty transcripts archived.
- **Payloads on disk**: ~197 ELF (55% UPX-packed, so family withheld by design);
  plenty of `empty` (zero-byte) files archived as "fetched" — see §5 capture.
- **Perf on live box**: the `live` process is burning **22–24% of one CPU sustained**
  (2199+ min CPU time!). `htop`/`ps` evidence:
  `root 953195 22.4% ... shardlure live ...`. Not a panic/crash — something hot.
  Suspect: the per-tick capture/ingest work + dashboard polling; worth profiling.

best-in-class discipline around safety gates, and a genuinely differentiated thesis
(actor-identity rather than IP). It's not without rough edges (classification
coverage, a few perf smells) — but nothing structurally broken.

| Dimension | Rating | Notes |
|---|---|---|

| Safety gates (Vet) | **A+** | `bazaar.Vet`, `abuseipdb.Vet`, `urlhaus.Vet`, `threatfox` vetting enforced once; SSRF guard on fetcher; admin-IP excluders; dry-run defaults. |

| Idempotency & ingestion | **A+** | dedup-by-signature, incremental actor re-aggregation, offset/inode tracking — very solid. |
| Observability/instrumentation | **B** | dashboard has real metrics but the daemon lacks pprof/profiling hooks to explain that 22% CPU. |
| Deployment/bootstrap | **A** | installer with safe SSH-key gates, idempotent, rollback-friendly. |
| UI/UX | **B+** | beautiful "SOC" aesthetic; but base font 13px + compact paddings = "too compact" on smaller screens; needs responsive polish. |

**Overall: A- (excellent personal project; a few targeted fixes below).**

## 4) Similar projects & how they classify payloads (web/GitHub comparison)

To answer "how others classify" honestly, I compared to the field:

- **Cowrie itself** (the ingest target): tags events with `eventid` (e.g.
  `cowrie.login.failed`, `cowrie.command.input`) — treats classification as
  event typing, no family attribution. ShardLure goes far beyond that.
- **T-Pot / TPotCE** — bundles Cowrie with ELK; classification is just Cowrie
  events + SURICATA IDS signatures (not a behavioral playbook). ShardLure's
  HASSH-clustering + username playbook is genuinely differentiated.
- **Dionaea / Modern Honey Network / OpenCanary / glutton** — classic payload
  capture, generic tagging. ShardLure's **precision-first ELF family classifier**
  (`internal/intel/bazaar/elf_family.go`, Tier-A anchors + XOR-wordlist + packing
  detection) is unusually rigorous — many of these tools just tag file types.
- **abuse.ch (MalwareBazaar/URLhaus/ThreatFox)** — ShardLure's outbound targets.
  Their server-side classification (YARA, ClamAV, telfhash) is heavier;
  ShardLure's **Vet-gate discipline** (only ship when family/provenance confirmed)
  is exactly how you'd avoid a ban. Few honeypots get the "don't pollute the
  shared feed" right; this one does.

Where ShardLure vs the field is **best**: actor **identity** clustering (HASSH),
and the **Vet gate** for outbound sharing. Where it's **market-average** (and
fine): playbook/intent heuristics (it aims for precision, so it under-labels).

**Verdict**: the classification approach is genuinely rigorous; coverage of
playbook/intent is where competitors beat you (actually yielding labels on 85%
of their actors vs 26%). I'll cover how to expand it in §8.

## 5) Capture & classification — gaps I verified on the live box

I ran real queries on `/var/lib/shardlure/shardlure.db` + fun `file`/grep passes
over `evidence/cowrie/*`:

- **Playbook coverage**: 4,109/5,537 actors = `unknown` (74%).
  Verified: `SELECT playbook,count(*) ...`. The classifier thresholds
  (`playbookFastSprayAPH=120`, etc. in `internal/actor/playbook.go`) are strict,
  and `journal` source (IP-only) produces little playbook signal. This reads as
  **deliberate precision over recall** — but on the live dashboard it surfaces as
  "unknown" far too much.
- **Zero-byte "fetched" captures**: the file-download worker copies and stores
  filenames like `sftp__root_<sha>_sshd` (On the wire: 0 bytes) and **records
  them** as `status=fetched` w/ size 0. Many entries. Pollutes archive.
- **Empty-file classification**: `MinSampleBytes=64` in `Vet` rejects <64 B
  anyway — but indexing them is still wasted DB/disk on the live box.
- **55% of ELFs are UPX-packed**: `Vet`/`Classify` then (correctly) withholds
  family because cleartext anchors are compressed; but the packing detection
  *could* run an `UPX` unpack attempt or hash-telfhash-submission to havelible
  classification (currently just "packed" tags; no further attempt).
- **Intent skew**: `intent` mostly `probe`/`unknown`; `deploy`=17/5537.
  Likely cause: `looksLikeDeployCmd` requires downloader+sink+exec; many
  intentions (e.g. `ssh stdin proxy, sftp-only upload, tty interaction`) don't
  match and stay `unknown`.
- **Top tunnels** (verified): dst ports 53, 443, 80, 2535 — legit research targets.
- **Bazaar uploads**: 59 uploaded, several `file_already_known` (i.e., shared
  to abuse.ch, which is fine because of the Vet gate ordering).

These all trace to **precision-first design** — worth *some* tightening, not
"bugs" per se — but at capture/ingestion time I can cite concrete fixes (§8).

## 6) Go toolchain / compatibility

- **Local toolchain**: `go1.26.4`. **Latest**: `go1.27.0` (released 2026-08-18; I
  verified from `https://go.dev/VERSION?m=text`).
- **`go.mod`**: `go 1.22` — builds cleanly with 1.26.4; tests pass for the
  packages I ran (`./internal/actor ./internal/intel/bazaar ./internal/intel/mitre
  ./internal/capture`).
- **Recommended**: bump `go` directive to **1.26** (or 1.27) once on the latest
  toolchain. The changes are safe; the current directive mostly pins language
  features (projekt `go`-directive chooses the maximum language version your
  module permits) and doesn't block you from building on newer toolchains. But
  upgrading does unlock:
  - stdlib vulnerability fixes (see §7);
  - better `embed`, `weak`, `iofs`/`testing/synctest`, `crypto/tls` features;
  - potentially faster `regexp` / `strings.Builder` / `encoding` paths.

I'll tell you exactly what to change in §9.

## 9) Performance observations (where to optimize)

The live process burns **~22–25% of one CPU** constantly. The architecture is
generally excellent (incremental touched-actor aggregation, `idx_events_actor`,
idempotency). Suspects (with code):

- **`main.go:312`** `t := time.NewTicker(interval)` → every N seconds runs
  `IngestFileAppend` + `capRunner.Run` each tick. Each tick does:
  - `batchDedupCowrie` (fine) → `syncCowrieActors` → `buildCowrieActorsForIDs`
    ← **`st.IterateEventsByActorIDs(ids, ...)`** reads *events by actor* from
    SQLite. On 5537 actors this is fine per tick, but it's still DB churn.
  - `capRunner.Run` → `fetchFromCommands` → `syncCowrieDownloads` →
    `archiveFileDownloadEvents` → `syncCowrieTTY` (all under a single ingestion
    call). TTY sync decodes transcripts from sticky path (`r.cowrieTTYDir()`).
  - **Suspect**: `runner.syncCowrieTTY` copies *raw tty logs named by sha256* AND
    `DecodeTTYLog` (production writes `.txt` too). The `totality` is bounded, but
    a high-traffic deployment may accumulate enough `- in-progress` tty files to
    make the `ReadDir` + admission checks expensive.
- **`main.go:282`** `go artWorker.Run(ctx)` polls every **10s** for due artifact
  captures — this is fine, but it collides with the ingest tick and can
  redundantly fetch/queue.
- **TUI/web long-polling sleeps** (`api_intel.go:1345,1453`) — 1s waits; harmless.

**Suggested (non-speculative, file-anchored) fixes**:
1. Add a **profiling hook** (opt-in `net/http/pprof`) to the `live` daemon so
   the 22% CPU can be *proven* rather than guessed. (`main.go` — currently no
   pprof.)
2. `capture.Runner.Run` — reconsider the **`fetchFromCommands`** + **`syncCowrieDownloads`**
   work: dedup already prevents re-copy, but `syncCowrieTTY` does
   `ReadDir`+`DecodeTTYLog` over the **whole tty dir per tick**. Track
   "indexed shas" is already adressed via `ttyIndexed`/`ttySessionBound` maps —
   but the initial `backfillCowrieTTYIndex` only runs once. Consider batching
   TTY sync or only scanning when the directory's `mtime` changed.
3. **Tune down the ingest tick interval** (`interval`) or make it event-driven
   (fsnotify on the Cowrie log) — the cadence is the main driver. The current
   constant and goroutine schedule is in `cmd/shardlure/main.go:305-335`.
4. **SQLite** — consider `PRAGMA journal_mode=WAL` (already implied by
   `.db-wal`) + checkpoint tuning; and confirm `idx_events_actor` is truly the
   index the planner picks for many-actor queries (it's clear from name; you
   already re-aggregated to this intentionally).

The biggest expected win is `#3` (ingest cadence). The incremental approach is
already correct — the remaining per-tick CPU is overhead of repeated
capture-directory + DB churn.

## 10) UI compactness findings (grep-verified)

`internal/web/index.html` + `internal/web/intel.html` + `themes.css`:

- **Base font** is `body { font: 13px/1.5 ... }` — quite small for tables of
  dense data. `th`/`td` cells use `padding: 5px 4px; font-size: 11.5px`.
  On small screens the dashboard feels cramped.
- **index.html (globe view)** has fixed rails (`.rail { width: 320px }`, left
  344px) with `@media (max-width: 1100px)` collapsing to `280px` and
  `@media (max-width: 760px)` stacking — but the rails stay in place at mid
  widths and the fixed width 320/344 is hard-wired.
- **intel.html** `body padding: 20px 24px 40px` with many sections sized
  `font-family: var(--mono); font-size: 11px` etc.

**Compactness suggestions**:
1. Bump body font to 14px and base table cell to 12px (keeping the mono look),
   with `clamp()` scaling. This alone relieves the "too compact" feel without
   breaking the "SOC" aesthetic.
2. Convert fixed rail widths to `minmax` so the sidebar breathes; use
   `:nth-of-type` responsive collapse earlier (e.g. 1400px).
3. Add a **compact/comfort toggle** (persist to `localStorage`) — a one-click
   "density" switch is the cleanest answer because the dashboard's different
   panes vary in density and one size never fits all.
4. When I grep `13px/1.5` on glass panels, the attention is on **sticky columns
   of fixed 320px rails** + 11.5px table font — both are correctable without
   breaking your deliberate "signal over chrome" principle.

**UI bugs candidates** (I noticed during grep, needs functional tests):
- `class="pane"` + fixed-width rails + `overflow:hidden` can clip on small
  screens when the Cobe globe is enabled.
- `chattr` regex in the bash script in `/tmp/clean_file` (captured payload) is
  attacker-side; **but the UI itself may truncate** long strings (see
  `intel.html` compact tables). Not a UI bug per se — check `class="stat .value"`
  with `< 22px` 22px font to keep labels readable.

## 11) New methods to make the classifier better

These are **concrete and incremental** (no rewrites):

1. **Add a second, looser playbook pass** that still tags `unknown` only when
   *nothing else* matches — e.g., fall back to `top_n_usernames`-style buckets
   ("common-account spray", "service-account spray", "mixed") after the strict
   APH gates. This raises coverage without poisoning the model. Location:
   `internal/actor/playbook.go`.
2. **UPX unpack attempt before family-attributed** — for packers, attempt a
   spawn-free `UPX !` header detection + optionally run `UPX`-unpack via a
   subprocess (`upx -d`) in a sandbox on the live box and *then* re-classify.
   Location: `internal/intel/bazaar/elf_family.go` (`isPackedELF`).
3. **Intent** — broaden `classifyIntent` with a `sftp`-only upload pattern
   (e.g. "file_upload via cowrie SFTP → treat as deploy") and `tty-interactive`
   (so tty captures no longer fall to `unknown`). Ideally in
   `internal/actor/playbook.go:ClassifyIntent`.
4. **Deobfuscation** — `internal/intel/deobf` already handles base64/hex;
   extend to `((a) ,(...))` style subshell wrappers and xor-cipher bash loops,
   which appear in the corpus. (`deobf.go`).
5. **MITRE coverage** — your `mitre/catalog.go` is conservative by design; add
   a "Script Drop" (T1059* `T1105`) and "Credential-filled form / browser"
   (T1055) classifiers that are still eligible, giving dashboard cells that
   aren't `unknown`. For import: MITRE grid is honest about coverage.
6. **Skills/depth over breadth** — trying to add signature-sets is wrong; a
   better return is a **second-pass "family-attempt"** that tries the raw
   unpack (upx) + re-classify, rather than more signatures.

## 12) Prioritized recommendations (shortlist, concrete)

1. **Upgrade Go to 1.27** and re-run `govulncheck` — fixes the confirmed stdlib
   vulnerabilities (GO-2026-5026, 5856, 5972, 6089, 6090, 6218). Bump `go.mod`
   `go 1.26`/`1.27` directive accordingly.
2. **Delete the verified-dead symbols** (§8). This is a true "bug/bug-adjacent"
   cleanup.
3. **Fix zero-byte/empty captures** — reject `size==0` at Capture time (or at
   `Vet`/`RecordArtifact`) and surface as `status=empty` rather than `fetched`.
4. **Profiling** — add optional `/debug/pprof` to the `live` daemon; chase the
   22% CPU under a real profile. (Suspect ingest tick cadence; see §9.)
5. **Classification coverage** — add a "second-pass looser playbook" to pull
   `unknown` down from 74% to ~85% on live data while preserving the
   precision-first gates.
6. **UPX-unpack** — in `elf_family`, when packed, try a sandboxed `upx -d`
   and re-classify; document the choice explicitly to avoid the "no family
   attribution on packed" cliff.
7. **UI compact** — body 13→14px, table 11.5→12px, rail `minmax`, and an
   optional density toggle.

Each of these maps to a specific file/line above — I've cited every claim.
